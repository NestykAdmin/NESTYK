## 0. เรื่องด่วน: ค่าสำหรับนักพัฒนาที่เปิดค้างอยู่

> เรื่องในข้อนี้ทำได้ทันที ไม่ต้องรองานสมัครสมาชิก
>
> ค่า env ที่ QA ได้รับจาก Railway ตั้งค่าเหล่านี้ไว้:
> - service "NESTYK — Backend API" (`.env.api`): `ALLOW_DEV_AUTH=true` และ `ALLOW_DEV_ROLE_GRANT=true`
> - service "NESTYK — Frontend" (`.env`): `EXPO_PUBLIC_APP_ENV=development`, `EXPO_PUBLIC_USE_DEV_AUTH=true` และ `EXPO_PUBLIC_ALLOW_DEV_ROLE_GRANT=true`
>
> ถ้าเซิร์ฟเวอร์ที่ใช้งานจริงใช้ค่าชุดเดียวกัน ทุกข้อด้านล่างเกิดได้แล้ววันนี้

### 0.1 API ยอมรับบัตรผ่าน (token) ปลอม — ร้ายแรงที่สุด

**สิ่งที่เกิดขึ้น**
- เมื่อ `ALLOW_DEV_AUTH=true` API จะเชื่อ token รูปแบบ `dev|<uuid>|<email>` โดยไม่ตรวจกับ Supabase และไม่ตรวจรูปแบบของ uuid หรืออีเมล (`apps/api/src/auth/guards/auth.guard.ts` บรรทัด 65-77)
- แอปส่ง token แบบนี้เองทุกครั้งที่ยังไม่มี session โดยไม่ดูค่าใดเลย (`apps/consumer-app/lib/api.ts` บรรทัด 66-67 และ `lib/dev-identity.ts`)

**ผลกระทบ (อนุมาน)**
- คนที่ไม่มีบัญชีเลยก็เข้า API ได้ ระบบจะสร้างผู้ใช้ใหม่ให้เมื่อเรียก `/auth/sync`
- ใครรู้ `supabase_user_id` ของคนอื่นก็ปลอมเป็นคนนั้นได้ ส่วน uuid ของบัญชี dev ฝังอยู่ในโค้ดแอปแล้ว (`lib/auth/dev-auth.ts` บรรทัด 12)
- ใส่อีเมลของคนอื่นได้ จึง "จองอีเมล" ไว้ก่อนได้ (ดูข้อ 4.2 กรณี A)
- เมื่อรวมกับข้อ 0.2 คนที่ไม่ได้ login ก็ได้สิทธิ์ `agent` หรือ `admin` ได้

**สิ่งที่ต้องทำ**
- [ ] ตั้ง `ALLOW_DEV_AUTH=false` บนเซิร์ฟเวอร์ที่ใช้งานจริง
- [ ] แอปที่ build ไปใช้งานจริงต้องไม่ส่ง dev token เมื่อไม่มี session (`lib/api.ts`)

### 0.2 ระบบแจกสิทธิ์ admin และ agent ให้เอง

**สิ่งที่เกิดขึ้น**
- **admin:** ทุกครั้งที่ login ผ่าน Supabase แอปจะเรียก `POST /auth/dev/roles` ขอ `admin` (`lib/auth/AuthContext.tsx` ฟังก์ชัน `ensureAdminRole` เรียกที่บรรทัด 147 และ 167) ยกเว้นแอปตั้ง `EXPO_PUBLIC_ALLOW_DEV_ROLE_GRANT` เป็น `'false'` ตรงตัว
- **agent:** แอปขอ `agent` ทุกครั้งที่เรียก API ฝั่งนายหน้า (`lib/agent-session.ts` บรรทัด 16 ถูกเรียกจาก `lib/agent-*-api.ts`, `places-api.ts`, `room-photos.ts`, `tenant-bills-api.ts`) โดย**ไม่ดู** `EXPO_PUBLIC_ALLOW_DEV_ROLE_GRANT`
- **API:** ให้สิทธิ์ตามที่ขอเมื่อ `ALLOW_DEV_ROLE_GRANT` เป็น `'true'` (`apps/api/src/auth/auth.service.ts` บรรทัด 27, 166-189, 212-216) ค่านี้เป็นตัวเดียวที่หยุดได้ทั้งการขอ admin และการขอ agent
- การสลับบทบาทในแอปไม่ดูบทบาทจริง ดูแค่ว่า login แล้วหรือยัง (`app/index.tsx` บรรทัด 522-534) และลิงก์ `nestyk://agent` หรือ `nestyk://admin` ก็สลับบทบาทได้ (บรรทัด 260-265) พอเข้าหน้านายหน้า แอปจะขอสิทธิ์ `agent` ให้ทันที

**ผลกระทบ**
- ผู้เช่าและเจ้าของห้องที่ได้บัญชีจากหนังสือจอง เมื่อ login เข้าแอปอาจได้สิทธิ์ admin ไปด้วย (อนุมาน)
- ถ้าเปิดให้สมัครเอง คนนอกจะได้ admin หรือ agent ทันที และใช้สิทธิ์นายหน้าค้นข้อมูลส่วนตัวของผู้ให้เช่าได้ (ดูข้อ 4.1)

**สิ่งที่ต้องทำ**
- [ ] ตั้ง `ALLOW_DEV_ROLE_GRANT=false` บนเซิร์ฟเวอร์ที่ใช้งานจริง
- [ ] เอา `ensureAdminRole` และ `ensureAgentSession` ออกจากแอปที่ build ไปใช้งานจริง หรือให้ทำงานเฉพาะตอนพัฒนา (`__DEV__`)
- [ ] ⚠️ **ก่อนปิด** ต้องแน่ใจว่านายหน้าตัวจริงทุกคนมีบทบาท `agent` ในตาราง `user_roles` แล้ว เพราะหลังปิด คนที่ยังไม่มีบทบาทนี้จะเปิดเมนูนายหน้าไม่ได้ และจะเห็นข้อความ "Dev role grant is disabled" ซึ่งเป็นข้อความสำหรับนักพัฒนา ตอนนี้ยังไม่มีทางอื่นให้บทบาทนายหน้า (การให้บทบาทอยู่ในแผน Phase 1 ข้อ A4)

### 0.3 ทางเข้าด้วยบัญชี dev ที่ฝังอยู่ในแอป

- ถ้า login ด้วย Supabase ไม่ผ่าน `signIn` จะลองใช้บัญชี dev แทน (`AuthContext.tsx` บรรทัด 132-142, 154-173)
- ทางนี้เปิดเมื่อ `EXPO_PUBLIC_USE_DEV_AUTH=true` หรือ `EXPO_PUBLIC_APP_ENV=development` (`lib/auth/dev-auth.ts` บรรทัด 6-8) อีเมลและรหัสผ่านตั้งต้นฝังอยู่ในโค้ด (บรรทัด 9-10) และหน้า login กรอกให้เอง (`login.tsx` บรรทัด 71-76)
- [ ] แอปที่ build ไปใช้งานจริงต้องปิดค่าทั้งสองนี้
- [ ] ตรวจว่า Supabase ที่ใช้งานจริงมีบัญชีที่ใช้อีเมล dev ตั้งต้นนี้ไหม ถ้ามี ให้เปลี่ยนรหัสผ่านหรือลบ

### 0.4 ไม่มีด่านกันค่าพวกนี้หลุดขึ้นระบบจริง

- ใน `apps/api` ไม่มีโค้ดที่ดูว่ากำลังรันบนระบบจริงหรือไม่ (ค้น `NODE_ENV` และ `isProduction` แล้วไม่พบ)
- [ ] **แนะนำ:** ให้ API ไม่ยอมเริ่มทำงานเมื่อรันบนระบบจริงแต่เปิด `ALLOW_DEV_AUTH` หรือ `ALLOW_DEV_ROLE_GRANT` ไว้ และให้ทำแบบเดียวกันตอน build แอป

| # | เรื่อง | ตัวเลือก | ข้อสรุป | เหตุผล |
|---|---|---|---|---|
| D1 | คนสมัครใหม่ได้บทบาทอะไร | ได้แค่ guest / เลือกบทบาทตอนสมัคร | **ได้แค่ `guest` ไม่มีหน้าเลือกบทบาท** (ปรับ 29 ต.ค. 2026) บทบาทอื่นได้มาจากงานจริง เช่น หนังสือจอง และการให้บทบาทนายหน้า/admin อยู่ในแผน Phase 1 ข้อ A4 | เอกสารนี้ครอบคลุมเฉพาะการเข้าสู่ระบบ และแผน Phase 1 กำหนดให้บทบาทผู้เช่าได้มาจากหนังสือจอง (ข้อ T3) |

- [ ] **จำกัดการค้นผู้ให้เช่า** `GET /agent/contracts/owner-users` (`agent-contracts.service.ts` ฟังก์ชัน `searchOwnerUsers` บรรทัด 2460-2503)

  - ลบผู้ใช้ใน Supabase ด้วย `auth.admin.deleteUser`
  - ลบข้อมูลในตาราง `users` หรือทำให้ระบุตัวตนไม่ได้ **และต้องเปลี่ยนหรือลบอีเมลในแถวนั้นด้วย** ไม่อย่างนั้นคนที่สมัครใหม่ด้วยอีเมลเดิมจะ sync ไม่ผ่าน (`users_email_key`)
  - จัดการข้อมูลที่ผูกกับผู้ใช้ เช่น สัญญาและบิล

### 4.2 ช่องโหว่ในการสร้างบัญชีจากหนังสือจอง (ต้องแก้ก่อนเปิดสมัคร)

**กรณี A — จองอีเมลของผู้เช่าไว้ก่อน แล้วลงนามแทน (ร้ายแรง)**
- เส้นทาง (อนุมาน):
  1. ผู้ไม่หวังดีสมัคร Supabase ด้วยอีเมลของผู้เช่าและรหัสผ่านของตัวเอง ผ่าน anon key ที่อยู่ในแอป หรือผ่าน dev token ในข้อ 0.1
  2. ถ้าไม่ต้องยืนยันอีเมล เขาได้ session ทันที แล้วเรียก `/auth/sync` ระบบจะสร้างแถวใน `users` ด้วยอีเมลนั้น
  3. ต่อมานายหน้าบันทึกหนังสือจองให้ผู้เช่าที่ใช้อีเมลนี้ `ensurePartyLogin` หาแถว `users` จากอีเมลเจอ จึงใช้บัญชีของผู้ไม่หวังดีเลย (`party-login.ts` บรรทัด 174-183)
  4. ระบบเขียนเบอร์โทร เลขบัตร และสัญชาติของผู้เช่าลงบัญชีนั้น เพิ่มบทบาท `tenant` (บรรทัด 198-218) และผูกผู้เช่ากับบัญชีนั้น
  5. ผู้ไม่หวังดีเห็นสัญญาและลงนามแทนผู้เช่าได้ เพราะระบบตรวจแค่ `tenant.user_id` (`agent-contracts.service.ts` ฟังก์ชัน `partiesFor` บรรทัด 581-585)
- ทำกับอีเมลของผู้ให้เช่าได้แบบเดียวกัน
- ไม่ต้องรอเปิดหน้าสมัคร เพราะตอนนี้ "สมัครเองไม่ได้" ปิดไว้แค่ปุ่มในแอป
- การตรวจ `assertTenantEmailNotShared` ที่มีแล้ว ณ commit `4833ace` (`party-login.ts` บรรทัด 119-141) **ไม่กันกรณีนี้** เพราะปฏิเสธเฉพาะอีเมลที่บัญชีผูกกับข้อมูลผู้เช่าของ lead อื่นอยู่แล้ว บัญชีที่เพิ่งสมัครยังไม่มีข้อมูลผู้เช่า
- ทางแก้: เปิด S5 (ยืนยันอีเมล) ปิด `ALLOW_DEV_AUTH` และให้ `ensurePartyLogin` ผูกเฉพาะบัญชีที่**เจ้าของยืนยันอีเมลเอง**แล้ว ระวังว่าบัญชีที่ระบบสร้างจากหนังสือจองถูกตั้งเป็น "ยืนยันอีเมลแล้ว" ตั้งแต่ตอนสร้าง (`email_confirm: true` ที่ `party-login.ts` บรรทัด 51) สถานะใน Supabase จึงแยกบัญชีกลุ่มนี้ไม่ได้ ต้องมีค่าที่บอกว่าเจ้าของยืนยันเองแล้ว

**กรณี B — นายหน้าคนใดก็ได้เขียนทับข้อมูลและเพิ่มบทบาทให้บัญชีใดก็ได้**
- ข้อมูลฝั่งผู้ให้เช่าในหนังสือจองมาจากค่าที่ส่งมาในคำขอ ระบบดึงค่าจากฐานข้อมูลมาแทนเฉพาะฝั่งผู้เช่า (`agent-contracts.service.ts` บรรทัด 3011-3017)
- `ensurePartyLogin` เขียนทับ ชื่อ นามสกุล เลขบัตร สัญชาติ และเพิ่มบทบาทให้บัญชีใดก็ได้ที่อีเมลตรงกัน โดยไม่ตรวจว่าเป็นลูกค้าของนายหน้าคนนี้ (`party-login.ts` บรรทัด 198-218)
- ณ commit `4833ace` ฝั่งผู้เช่ามี `assertTenantEmailNotShared` ซึ่งกันกรณีอีเมลเป็นของผู้เช่าคนอื่นของ lead อื่นที่ชื่อและเลขบัตรไม่ตรงกัน แต่ยังไม่ครอบคลุมฝั่งผู้ให้เช่า และไม่กันอีเมลของบัญชีที่ไม่มีข้อมูลผู้เช่า เช่น บัญชีนายหน้าหรือ admin
- ผล:
  - นายหน้า B ใส่อีเมลของผู้ใช้คนอื่น (ผู้ให้เช่าของนายหน้า A, นายหน้าคนอื่น หรือ admin) แล้วเปลี่ยนเลขบัตรของคนนั้นได้ถาวร โดยไม่มีประวัติให้ย้อนดู
  - หลังเปิดสมัคร ชื่อที่ผู้ใช้แก้เองจะถูกเขียนทับทุกครั้งที่นายหน้าบันทึกฉบับร่าง
- ทางแก้: ไม่เขียนทับข้อมูลของบัญชีที่มีอยู่แล้ว (หรือเขียนเฉพาะช่องที่ว่าง) และไม่เพิ่มบทบาทให้บัญชีที่ไม่ได้เป็นลูกค้าของนายหน้าคนนั้น

**กรณี C — บัญชีถูกสร้างก่อนที่การบันทึกจะสำเร็จ**
- `ensurePartyLogin` สร้างบัญชี Supabase และ commit แถว `users` ที่มีเลขบัตรและบทบาทไปก่อน (`party-login.ts` บรรทัด 47-52, 180-220) ส่วนการบันทึกหลักเริ่มทีหลัง (`agent-contracts.service.ts` บรรทัด 3119)
- ถ้าการบันทึกล้มทีหลัง หรือนายหน้าพิมพ์อีเมลผิด จะเหลือบัญชีที่เก็บเลขบัตรของผู้เช่าไว้ใต้อีเมลของคนอื่น และเจ้าของอีเมลตัวจริงจะสมัครเองไม่ได้ (อนุมาน)
- ทางแก้: สร้างบัญชีหลังบันทึกสำเร็จ หรือสร้างตอนส่งเอกสารแทนตอนบันทึกฉบับร่าง

**กรณี D — อีเมลซ้ำกับข้อมูลเก่าในตาราง `users`**
- `/auth/sync` หาผู้ใช้จาก `supabase_user_id` อย่างเดียว (`auth.service.ts` บรรทัด 83-86) แต่ตาราง `users` ห้ามอีเมลซ้ำ (`users_email_key`)
- ถ้ามีแถวเก่าที่ใช้อีเมลนั้นแต่ไม่มี `supabase_user_id` คนที่สมัครด้วยอีเมลเดียวกันจะ sync ไม่ผ่าน น่าจะได้ HTTP 500 เพราะไม่มีตัวจัดการ error กลาง (อนุมาน)
- ทางแก้: ตรวจว่ามีข้อมูลแบบนี้ไหม ถ้ามี ให้ `sync` ผูกกับแถวเดิม **เฉพาะเมื่ออีเมลยืนยันแล้ว** ถ้าผูกโดยไม่ยืนยันอีเมล คนที่สมัครด้วยอีเมลของผู้เช่าจะได้ข้อมูลของผู้เช่าไป

**กรณี E — สมัครค้างไว้แต่ยังไม่ยืนยันอีเมล**
- ถ้านายหน้าบันทึกหนังสือจองด้วยอีเมลนั้น `ensurePartyLogin` จะหาบัญชี Supabase เดิมเจอแล้วผูกด้วย (`party-login.ts` ฟังก์ชัน `findSupabaseUserId` และบรรทัด 56-63) บัญชีนั้นยังไม่ยืนยัน และรหัสผ่านเป็นรหัสที่คนสมัครตั้งเอง
- ต้องกำหนดว่าจะจัดการอย่างไร เช่น ส่งอีเมลเชิญหรืออีเมลรีเซ็ตรหัสผ่านไปที่บัญชีนั้น

### 4.3 ใช้ต่อได้ แต่ต้องระวัง

- `POST /auth/sync` ใช้ต่อได้ แต่ระบบแยกชื่อเต็มด้วยช่องว่าง ชื่อต้นที่มีช่องว่างจะถูกแยกผิด แอปจึงควรส่ง `firstName` และ `lastName` ใน `PATCH /auth/profile` อีกครั้ง
- `PATCH /auth/profile` จำกัดชื่อและนามสกุล 255 ตัว และเบอร์โทร 50 ตัว แต่ไม่กันค่าว่าง แอปต้องกันเอง
- `profile_completed` เป็นจริงได้ทั้งที่ยังไม่ได้กรอกชื่อ เพราะ `first_name` มีค่าตั้งต้นเป็น `'User'` (`user.entity.ts` บรรทัด 20) **แนะนำ:** ไม่นับ `'User'` เป็นชื่อ

### 5.1 หน้าสมัคร (เช่น `app/register.tsx`)

**ไม่ควรถามตอนสมัคร**
- เลขบัตรประชาชนหรือพาสปอร์ต และสัญชาติ: ใช้ตอนทำสัญญา และนายหน้ากรอกให้อยู่แล้ว
- รูปโปรไฟล์: เพิ่มทีหลังได้ผ่าน `POST /auth/profile/avatar` (endpoint นี้รับ URL ยาวไม่เกิน 512 ตัว ไม่ได้รับไฟล์)

### 5.2 ขั้นตอนการทำงาน

- [ ] แก้ปุ่มสมัครใน `login.tsx` บรรทัด 421 ให้เปิดหน้าสมัคร
- [ ] เพิ่มฟังก์ชัน `signUp` ใน `AuthContext.tsx`
  1. เรียก `supabase.auth.signUp` พร้อม
     - `options.data.full_name` = ชื่อ + นามสกุล
     - `options.captchaToken` (ถ้าเปิด S9)
  2. ยังไม่ได้ session กลับมา ให้ไปหน้ากรอกรหัส 6 หลัก (ข้อสรุป Q1 ใน flow design ใช้รหัส ไม่ใช้ลิงก์)
  3. ผู้ใช้กรอกรหัส → `verifyOtp({ email, token, type: 'signup' })` → `applySession` → `POST /auth/sync` → `PATCH /auth/profile` (ชื่อ นามสกุล เบอร์โทร)
- [ ] **สร้าง session หลังยืนยันรหัส และจากลิงก์ของ Facebook / Apple (F9)**
  - การยืนยันอีเมลใช้รหัส 6 หลักจึงไม่ต้องรับลิงก์ แต่ Facebook / Apple ต้องรับลิงก์กลับเข้าแอป ตอนนี้ตัวรับลิงก์เดิมใช้แค่สลับบทบาทและแท็บ (`app/index.tsx` ฟังก์ชัน `handleDeepLinkUrl`) ยังไม่มีโค้ดสร้าง session จากลิงก์
  - session ใหม่ต้องผ่าน `syncProfile` และ `applySession` แบบเดียวกับ `AuthContext.tsx` บรรทัด 144-149 เพราะ `lib/api.ts` อ่าน token จากที่แอปเก็บเอง (`nestyk.auth.session.v1`) ถ้าไม่ได้เก็บ แอปจะส่ง dev token แทน
  - ตัวรับลิงก์เดิมเทียบด้วย `includes()` กับคำว่า tenant, landlord, owner, agent, admin, services, guest, search, viewing path ของลิงก์กลับเข้าแอปต้องไม่มีคำเหล่านี้
- [ ] **ต่ออายุ token (ทีมทำแล้วบางส่วน ณ commit `4833ace`)**
  - ทำแล้ว: `lib/api.ts` ขอ token ล่าสุดจาก Supabase และต่ออายุเมื่อได้ 401 ส่วน `lib/auth/supabase.ts` หยุดและเริ่มการต่ออายุตามสถานะของแอป
  - ยังเหลือ: การต่ออายุใน `lib/api.ts` ทำเฉพาะคำขอที่ไม่ได้ส่ง token มาเอง แต่ `/auth/sync` ใน `AuthContext.tsx` (ตอนเปิดแอป, `refreshProfile`, login) ส่ง token ที่เก็บไว้ตอน login เอง ถ้าเปิดแอปใหม่หลัง token หมดอายุ (ตั้งต้น 1 ชั่วโมง) แอปจะล้าง session เงียบๆ ทุกครั้งที่ sync ไม่ผ่าน รวมถึงตอนเน็ตหลุด (`AuthContext.tsx` บรรทัด 101-111) (อนุมาน)
  - ยังเหลือ: มีจุดให้ลงทะเบียนตัวจัดการ session หมดอายุ (`setSessionExpiredHandler`) แต่ยังไม่มีโค้ดไหนลงทะเบียน แอปจึงไม่ออกจากระบบและไม่แจ้งผู้ใช้เมื่อต่ออายุไม่ได้
- [ ] **ล้างค่าที่จำไว้ตอน sign out:** `ensureAgentSession` จำผลของผู้ใช้คนก่อนไว้ (`agent-session.ts` บรรทัด 9, 20-27) ผู้ใช้คนที่สองบนเครื่องเดียวกันจะข้ามการ sync
- [ ] **ตรวจบทบาทจริงก่อนสลับบทบาท:** เมนูเลือกบทบาทและลิงก์ `nestyk://agent`, `nestyk://admin` ควรเปิดได้เฉพาะเมื่อผู้ใช้มีบทบาทนั้นใน `session.roles`
- [ ] **หน้ากรอกรหัส 6 หลัก:** มีปุ่ม "ส่งรหัสอีกครั้ง" (`supabase.auth.resend`) และเวลารอก่อนกดซ้ำ
- [ ] **รหัสผิดหรือหมดอายุ:** แสดงข้อความและปุ่มขอรหัสใหม่
- [ ] **ลืมรหัสผ่าน:** ทำปุ่มเดิมให้ใช้ได้ (`resetPasswordForEmail`) พร้อมหน้าตั้งรหัสผ่านใหม่
- [ ] **ลบบัญชี:** ปุ่มในหน้าโปรไฟล์หรือหน้าตั้งค่า มีหน้าให้ยืนยันก่อนลบ
- [ ] **ข้อความ error ที่ต้องมี** (ตอนนี้ `signIn` ส่ง `error.message` ของ Supabase ต่อไปทุกกรณี `AuthContext.tsx` บรรทัด 141)
  - อีเมลนี้มีบัญชีแล้ว → แนะนำให้ไป login หรือกดลืมรหัสผ่าน
  - ยังไม่ได้ยืนยันอีเมล → บอกให้เช็คอีเมล พร้อมปุ่มส่งอีเมลอีกครั้ง
  - รหัสผ่านไม่ตรงกฎ (error code `weak_password`)
  - ขอบ่อยเกินไป (rate limit)
  - session หมดอายุ → บอกให้ login ใหม่
  - เชื่อมต่อไม่ได้
- [ ] **ข้อความทั้งหมด** เพิ่มใน `packages/i18n` ครบ 4 ภาษา (th / en / zh / ja) ลบ `signupUnavailable` กับ `resetUnavailable` เมื่อไม่ใช้แล้ว และแก้ข้อความกฎรหัสผ่านเดิม (`th.ts` บรรทัด 254) ให้ตรงกับ D4

### คำถามถึงทีม
1. การค้นผู้ให้เช่าข้ามนายหน้า (`owner-users`) ตั้งใจให้เป็นสมุดรายชื่อรวมไหม ถ้าใช่ ควรคืนเลขบัตรเต็มไหม (D9)
2. คู่สัญญาเห็นเลขบัตรและเบอร์โทรของอีกฝ่ายในสัญญา (`contractForParty` คืนข้อมูลสัญญาทั้งก้อน `agent-contracts.service.ts` บรรทัด 2069-2074) ตั้งใจไหม
3. บัญชีที่สร้างจากหนังสือจองได้บทบาท `tenant`/`landlord` แต่ไม่ได้บทบาท `guest` ต่างจากบัญชีที่ sync สร้าง ตั้งใจไหม
4. Supabase ที่ใช้งานจริงมี SMTP ของบริษัทแล้วหรือยัง
