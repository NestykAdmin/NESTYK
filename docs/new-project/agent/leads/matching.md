## 1. เป้าหมาย

จับคู่ห้องของ agent กับ lead โดยแยก 3 ชั้น:

1. **Hard set** — กรองห้องด้วยเงื่อนไขที่วัดได้ (SQL / query)
2. **Deterministic score** — คิดคะแนนจากเกณฑ์และน้ำหนักที่กำหนดไว้ ตรวจซ้ำได้
3. **AI explanation** — สรุปเหตุผล/ข้อควรตรวจสอบจาก shortlist โดยไม่ตัดสินความเข้ากันได้แทนกฎธุรกิจ

คะแนน `84%` หมายถึง **ความตรงกับเกณฑ์ที่ระบุ** ไม่ใช่โอกาส 84% ที่ลูกค้าจะจอง ต้องแสดงความครบของข้อมูลหรือ `confidence` แยกจากคะแนน

ความครบของฟอร์ม matching **ไม่เปลี่ยน** `leads.status` (`new` / `inprogress` / `lost` / `booked`)

## 2. เงื่อนไขเปิด matching (พร้อมจับคู่)

ตาม [add-lead-groups.md](./add-lead-groups.md) ต้องมีอย่างน้อย:

| Lead | ความหมาย |
|------|----------|
| `budget_max` | งบสูงสุดต่อเดือน (ตัวเลขบวก) |
| `lead_locations` ≥ 1 แถว | หมุดค้นหาอย่างน้อย 1 จุด (lat/lng) + `leads.radius_km` |

สองส่วนนี้เพียงพอสำหรับ **ดึง candidate set เบื้องต้น** แต่คะแนนจากข้อมูลเพียงสองมิติยังไม่ละเอียด ให้แสดงว่าเป็น “คะแนนเบื้องต้น” พร้อมความครบของข้อมูล; ถ้าต้องการอันดับที่มีประโยชน์ควรถามเพิ่มอย่างน้อยหนึ่งข้อ เช่น ประเภทห้อง ระยะเช่า หรือวันย้ายเข้า

Lead เก่าที่มีแค่ `province` / `locations` (ก่อนมีหมุด) ถือว่า **ยังไม่พร้อมจับคู่** จนกว่า agent จะปักหมุด

### 2.1 หมุดค้นหาแบบจัดอันดับ (สูงสุด 3 จุด)

- ตาราง `lead_locations` — `rank` 1–3 (1 = สำคัญที่สุด), `place_id`, `name`, `latitude`, `longitude`, `province`, `district`
- รัศมี **ใช้ร่วมกันทุกหมุด** จาก `leads.radius_km` (1 / 3 / 5 กม.)
- `leads.province` = จังหวัดของหมุดอันดับ 1; `leads.locations` = เขตของทุกหมุด (ไว้ใช้กับตัวกรองรายการ Lead เท่านั้น ไม่ใช้จับคู่)
- คอลัมน์หมุดเดี่ยวเดิมบน `leads` (`location_place_id`, `location_name`, `latitude`, `longitude`) ไม่ถูกเขียนแล้ว — ข้อมูลเดิมย้ายเป็นหมุดอันดับ 1 ใน migration `20260924-lead-locations.sql`

สถานะ UI: **“ข้อมูลหลักพร้อมสำหรับจับคู่ห้อง”** — ยังไม่มี API คำนวณคะแนนจริง

## 3. ชั้น Hard set (ดึง shortlist)

### บังคับเสมอ

| Lead | ห้อง | หมายเหตุ |
|------|------|----------|
| `budget_max` | `rent_room_prices` | ตัดห้องที่ราคาเกินงบ |
| หมุด + `radius_km` | `COALESCE(rent_room.latitude, property.latitude)` / longitude | ห้องต้องอยู่ภายใน **2 × รัศมี** ของหมุดใดหมุดหนึ่ง (ดูสูตรใน 3.1); ห้องไม่มีพิกัดไม่ผ่าน และแสดงเป็นข้อมูลห้องที่ต้องแก้ไข |
| — | `is_scout_room = true`, `created_by_user_id = agent`, `room_status = available` | ห้องใน inventory ของ agent ที่ยังเสนอได้; **ไม่บังคับ** `visibility = published` เพราะห้อง private ก็แชร์ลิงก์ได้ |

### ใส่เมื่อ lead กรอกแล้วเท่านั้น (null = ไม่ตัดทิ้ง)

| Lead | ห้อง | หมายเหตุ |
|------|------|----------|
| `lease_duration_months` | `rent_room_prices.contract_type_id` / `term_months` | ถ้าระบุ ต้องมีราคาในระยะสัญญานั้นและใช้ราคานั้นเทียบงบ |
| ประเภทห้อง/จำนวนห้องนอน | `room_type` / `layout_values` | Hard filter เฉพาะเมื่อ Lead ระบุว่าเป็น **เงื่อนไขบังคับ**; มิฉะนั้นให้คะแนนแบบ soft |
| ต้องเลี้ยงสัตว์/สูบบุหรี่/มีที่จอดรถ | นโยบายที่ยืนยันแล้วของห้อง | ใช้ Hard filter ได้เมื่อมีค่าฝั่งห้องแบบ `allowed` / `not_allowed` / `unknown`; facility tag ที่ไม่มีอยู่ไม่ได้แปลว่าห้าม |

### 3.1 ระยะทางและคะแนนทำเล

1. **Prefilter (bounding box, ใช้ index `idx_lead_locations_lat_lng` / พิกัดห้อง):** ต่อหมุดแต่ละจุด ให้ `R = 2 × radius_km`
   `dLat = R / 111.32`, `dLng = R / (111.32 × cos(lat))` แล้วกรอง `lat BETWEEN pin.lat ± dLat AND lng BETWEEN pin.lng ± dLng` (OR ระหว่างหมุด)
2. **ระยะจริง:** Haversine (`distanceMeters` ใน `apps/api/src/agent/places/nearby-places.ts`) ระหว่างห้องกับทุกหมุด
3. **distanceScore ต่อหมุด:** `100` ถ้า `d ≤ radius`; ลดเชิงเส้นเป็น `0` ที่ `d = 2 × radius`; เกินกว่านั้น = ไม่ผ่านสำหรับหมุดนั้น
4. **น้ำหนักตามอันดับ:** อันดับ 1 = `1.00`, อันดับ 2 = `0.85`, อันดับ 3 = `0.70`
5. **locationScore = max(distanceScore(pin) × weight(pin.rank))** — ใช้หมุดที่ให้คะแนนสูงสุด และแสดงให้ agent เห็นว่าห้องตรงกับหมุดไหน (เช่น “ใกล้ BTS อโศก · 1.2 กม.”)

ระยะเป็นเส้นตรง ไม่ใช่เวลาเดินทาง เมื่อข้อมูลห้องมากขึ้นให้ย้ายไปใช้ PostGIS (`geography` + `ST_DWithin`) แทน bounding box

**กฎ “ไม่ระบุ”:** ค่า `null` ฝั่ง Lead ต้องไม่ตัดห้องออกจาก hard set; ค่าฝั่งห้องที่ `unknown` ต้องไม่ถูกตีความว่า `false` และควรติดป้าย **ต้องสอบถาม** แทนการให้คะแนนเต็ม

**ราคาที่ใช้เทียบงบ**

- มี `lease_duration_months` → ใช้ราคาในระยะสัญญานั้นเท่านั้น; ถ้าไม่มีราคานั้น ห้องไม่ผ่าน hard set
- ไม่มี → ห้องผ่านเมื่อมี **อย่างน้อยหนึ่ง** ระยะสัญญาที่ราคา ≤ `budget_max`; บันทึกระยะสัญญา/ราคาที่ใช้เทียบและแสดงให้ agent เห็น อย่าใช้ 12 เดือนเป็นค่า default โดยไม่ได้ถาม Lead
- ราคาเป็นค่าเช่าต่อเดือน; เงินประกัน/ล่วงหน้าเป็นอีกเกณฑ์หนึ่ง ถ้าจะกรองยอดวันเข้าอยู่ต้องมี `max_upfront_budget` ของ Lead
- ห้องไม่มีราคาที่ตรวจสอบได้ไม่ควรได้คะแนนหรือหลุดเข้า shortlist แบบเงียบ ๆ ให้แสดงเป็นข้อมูลห้องที่ต้องแก้ไข

ถ้าได้ 0 ห้อง ให้แจ้งว่าเงื่อนไขใดทำให้ผลลัพธ์ว่าง พร้อมเสนอการผ่อน **เฉพาะเงื่อนไขที่ Lead ยอมยืดหยุ่น**; ห้ามเพิ่มห้องที่ไม่ผ่านข้อบังคับโดยไม่แจ้ง

ผล **“ใกล้เคียง”** ควรเป็นอีกกลุ่มแยกจากผลที่ผ่านทุกข้อ: จัดอันดับห้องที่ต่างจากเงื่อนไขที่ยืดหยุ่นได้ เช่น ราคาสูงกว่างบไม่เกินจำนวนเงินที่ Lead ยอมรับหรืออยู่เขตข้างเคียง พร้อมบอก `overBudgetBy` / `outsideAreaBy` และเหตุผลที่ไม่ผ่าน ห้ามนำไปรวมกับจำนวนห้องที่ match ตรงหรือให้คะแนนสูงเท่าห้องที่ผ่านครบ ถ้ายังไม่มีข้อมูลความยืดหยุ่น ให้ agent เลือกว่าจะขยายเงื่อนไขใดก่อน

## 4. ชั้น Soft score และ AI explanation

คำนวณคะแนนจากข้อมูลที่มีโครงสร้างก่อน แล้วคัด top K เพื่อส่งให้ AI อธิบาย; ไม่ส่งทุกห้องเข้าพร้อมกัน คะแนนต้องคงที่เมื่อ input และ `scoring_version` เดิมเหมือนกัน น้ำหนักของเกณฑ์เป็น config ที่ปรับหลังทดสอบกับ agent ได้

| กลุ่ม | ฟิลด์ Lead | บทบาทในคะแนน |
|--------|-----------|----------------|
| งบ | `budget_max`, ราคาของระยะสัญญาที่ใช้ | ความห่างจากงบสูงสุด; **ไม่หักคะแนนเพราะห้องถูกกว่า `budget_min`** เว้นแต่ Lead ระบุว่าเป็นข้อกำหนดจริง |
| ทำเล | หมุดจัดอันดับ + รัศมีร่วม (`locationScore` ใน 3.1), `preferred_location` | ความใกล้ / ความสะดวก |
| ห้อง | ประเภทห้อง, ระยะเช่า | fit สเปก vs ยืดหยุ่น |
| ไลฟ์สไตล์ | pets, car, smoker, `occupant_count` | ใช้เฉพาะเมื่อมีนโยบาย/ความจุที่ยืนยันได้ ไม่อนุมานจากการไม่มี facility tag |
| ไทม์ไลน์ | วันที่ย้ายเข้าที่มีโครงสร้าง + `available_from_date` | พร้อมเข้าอยู่; `move_in_plan` ข้อความอิสระใช้เป็นโน้ตจนกว่าผู้ใช้ยืนยันวันที่ |

**ไม่ใช้และไม่ส่งให้ AI:** ชื่อ เบอร์ อีเมล สัญชาติ อาชีพ ประเภทวีซ่า หรือข้อมูลระบุตัวบุคคลอื่น; ข้อมูลเหล่านี้ไม่ใช่ความต้องการห้องและไม่มีเกณฑ์ห้องที่ตรวจสอบได้ให้เทียบ

ถ้าฟิลด์ที่มีผลต่อน้ำหนักยังไม่ระบุ ให้แสดง `unknown` และลด **ความมั่นใจของคะแนน** แทนการสมมติว่าเข้ากันได้เต็ม 100% แสดงทั้งข้อที่ตรง ข้อที่ไม่ตรง และข้อที่ต้องสอบถาม

**ถ้าจะให้ AI มีส่วนในคะแนน:** ให้ AI ประเมินเฉพาะเกณฑ์เชิงคุณภาพที่กฎปกติตีความยาก เช่น ข้อความทำเลที่ Lead ระบุเทียบกับ `nearbyPlaces` โดยคืนคะแนนย่อยและหลักฐานจาก field ที่ส่งให้ ภาคนี้ควรมีเพดานน้ำหนักเล็ก (ข้อเสนอเริ่มต้น: ไม่เกิน 10/100 คะแนน) คะแนนรวมยังคำนวณใน server และ AI ห้ามเปลี่ยนผล hard filter ถ้า AI ล้มเหลว ให้ข้ามคะแนนย่อยนี้และลดความครบของคะแนน

ก่อน implement ต้องกำหนดสูตรย่อย ช่วงคะแนน และน้ำหนักแต่ละเกณฑ์ใน `scoring_version` อย่างชัดเจน เช่น ราคา ทำเล ประเภทห้อง ระยะเช่า วันย้าย และคะแนนเชิงคุณภาพ พร้อม `coverage` ว่ามีข้อมูลให้ประเมินได้กี่ส่วนของน้ำหนักทั้งหมด อย่า normalize เฉพาะ field ที่มีจน Lead ซึ่งให้ข้อมูลน้อยได้ 100% ง่ายกว่าคนที่กรอกครบ

## 5. Flow

```
Lead พร้อมจับคู่? (budget_max + หมุด ≥ 1)
        │
        ▼
Hard filters → candidate set ห้องของ agent
        │
        ▼
Deterministic score → sort + top K
        │
        ▼
AI prompt (เฉพาะ preferences + room facts ที่อนุญาต) → qualitativeScore + reasons + unknowns
        │
        ▼
แสดงคะแนน, ความมั่นใจ, เหตุผล และข้อที่ต้องตรวจสอบให้ agent
```

อย่าส่ง raw entity, contact หรือโน้ตภายในเข้าโมเดล — ใช้ allowlist ของข้อมูลที่อ่านได้และมีขนาดคงที่ ข้อความประกาศ/โน้ตที่ส่งเข้า AI เป็น **ข้อมูลประกอบ** ไม่ใช่คำสั่งให้ AI ทำตาม

ผล AI ควรเป็น JSON schema เช่น `{roomId, qualitativeScore, reasons[], tradeoffs[], unknowns[]}` โดย `qualitativeScore` เป็น `0–10` หรือ `null` เมื่อไม่มีหลักฐาน และแต่ละเหตุผลมี `field`/`evidence` ที่อ้างถึงข้อมูลจริง ตรวจ schema, `roomId` ต้องอยู่ใน top K, จำกัดจำนวน/ความยาวข้อความ และใช้เหตุผลที่สร้างจากกฎแทนเมื่อ AI ล้มเหลว [Gemini structured output](https://ai.google.dev/gemini-api/docs/structured-output) ช่วยบังคับรูปแบบ JSON แต่แอปยังต้องตรวจค่าทางความหมายเอง

คะแนนและเหตุผลควรบันทึก `lead_id`, `room_id`, `scoring_version`, `lead_updated_at`, `room_updated_at`, `generated_at` เพื่อรู้ว่า stale เมื่อข้อมูลเปลี่ยน; refresh ก่อนนำไปใช้จริง

ก่อนเปิดใช้คะแนน % ให้ทำชุดตัวอย่าง Lead–ห้องที่ agent ให้ความเห็นว่าเหมาะ/ไม่เหมาะ แล้วตรวจอันดับ, กรณี 0 ผลลัพธ์, ข้อมูลขาด, คะแนนเปลี่ยนหลังแก้ข้อมูล และเหตุผลที่ AI กล่าวเกินข้อมูลจริง รวมทั้งบันทึกสูตร/น้ำหนัก/เกณฑ์ผ่านที่ใช้จริงเพื่อทดสอบซ้ำ [NIST AI RMF](https://airc.nist.gov/airmf-resources/playbook/measure/) เน้นการวัดความถูกต้อง ความน่าเชื่อถือ และข้อจำกัดของระบบ AI

## 5.1 ผลจับคู่เบื้องต้น (คำนวณที่ server เมื่อนายหน้ากดจับคู่)

> ตั้งแต่ 2026-10-02 การจับคู่ทำที่ API เมื่อกดปุ่ม "จับคู่ห้อง" และเก็บผลไว้ — รายละเอียดปุ่ม ค่าตั้งค่ารายลีด และ endpoint ดู [match-settings.md](./match-settings.md)

สูตรอยู่ที่เดียวใน `apps/api/src/agent/leads/lead-matching.ts` (คัดห้อง + เทียบรายเกณฑ์ + คะแนนรวม) แอปแสดง `comparison` ที่ server ส่งมาทั้งในการ์ดห้องของ Lead detail และหน้าเทียบห้อง คะแนนจึงตรงกันทุกจุด (`apps/consumer-app/lib/lead-room-compare.ts` เหลือเฉพาะ type และตัวช่วยแสดงผล)

- **ห้องที่นำมาคิด:** ห้อง `available` ของ agent ที่ยังไม่มีลีดจอง (`leads.status = booked`) อยู่ในกรอบพิกัดรอบหมุด (2× รัศมี) และราคาเริ่มต้นไม่เกินงบ — คัดด้วย SQL ใน `AgentListingsService.matchCandidates` ไม่มีเพดาน 200 ห้องแบบเดิม
- **Hard filter (คัดกรองเบื้องต้น):** มีพิกัด (ห้องหรือตึก) · ราคาไม่เกิน `budget_max` (ใช้ราคาตาม `lease_duration_months` ถ้าห้องมีราคานั้น ไม่งั้นใช้ราคาถูกสุด) · อยู่ภายใน 2× รัศมีจากหมุดใดหมุดหนึ่ง — **ระยะสัญญาไม่ใช่ตัวกรองแล้ว** ห้องที่ไม่มีระยะสัญญาตรงยังแสดง แต่เสียคะแนนข้อนี้

### กติกาเกณฑ์: ใช้เฉพาะช่องในแท็บ “จับคู่ห้อง”

เกณฑ์ที่นำมาคิดคะแนน = **เฉพาะช่องในแท็บ 2 “จับคู่ห้อง” ของฟอร์มสร้าง/แก้ไข Lead** เท่านั้น ข้อมูลแท็บโปรไฟล์ (สัตว์เลี้ยง ใช้รถ สูบบุหรี่ จำนวนคน ฯลฯ) **ไม่นำมาคิด**

> **ถ้าในอนาคตแท็บ “จับคู่ห้อง” มีช่องเพิ่ม** ต้องเพิ่มแถวใน `compareLeadRoom()` (`apps/api/src/agent/leads/lead-matching.ts` → `COMPARE_KEYS`) ให้มี `status` + `score` และข้อนั้นจะเข้าค่าเฉลี่ยอัตโนมัติ เพิ่มช่องนั้นใน `matchInputHash` และเพิ่ม `SCORING_VERSION` · ฝั่งแอปเพิ่ม type ใน `lead-room-compare.ts` (`COMPARE_KEYS`) พร้อมข้อความใน `agent.leads.matchRoom.*` และอัปเดตตารางนี้

| เกณฑ์ | ลีด (แท็บจับคู่ห้อง) | ห้อง | คะแนนข้อนี้ | สถานะ |
|---|---|---|---|---|
| งบ | `budget_min–max` | ราคาที่ใช้จับคู่ | 100 (ผ่าน hard filter แล้ว) | ผ่าน |
| ทำเล | หมุด 1–3 + `radius_km` | ระยะจากหมุดที่ดีที่สุด | คะแนนทำเล §3.1 × น้ำหนักหมุด (1 / 0.85 / 0.7) | ผ่าน / เกินรัศมี X กม. |
| ประเภทห้อง | `desired_room_type_code` | `roomTypeCode` | ตรง 100 · ไม่ตรง 0 | ผ่าน / ไม่ตรง |
| ระยะสัญญา | `lease_duration_months` | `prices[].termMonths` | มีราคาระยะนั้น 100 · ไม่มี 0 | ผ่าน / ไม่ตรง |
| วันย้ายเข้า | `move_in_plan` (ISO) | `availableFromDate` | ว่างทัน 100 · ว่างช้า ลดเชิงเส้นจนเป็น 0 ที่ 30 วัน (`MOVE_IN_GRACE_DAYS`) | ผ่าน / ว่างช้ากว่า N วัน |

`preferred_location` (โน้ตทำเลข้อความอิสระ) อยู่ในแท็บเดียวกันแต่ **ไม่คิดคะแนน** เพราะเทียบกับห้องแบบเชื่อถือได้ไม่ได้

### คะแนนรวม

- **คะแนนรวม = ค่าเฉลี่ยเท่ากันทุกข้อ** ของเกณฑ์ที่ตัดสินได้ ปัดเป็นจำนวนเต็ม (`overallScore()`)
- **ไม่นับในค่าเฉลี่ย:** ลีดไม่ได้ระบุ (`unspecified`) · ห้องไม่มีข้อมูล (`unknown`) · ประเมินไม่ได้ เช่น `move_in_plan` เป็นข้อความอิสระ (`notEvaluable`)
- ตัวอย่าง: ลีดต้องการ 3 ห้องนอน ห้องเป็นสตูดิโอ ข้ออื่นผ่านหมด → (100+100+0+100+100)/5 = **80** ไม่ใช่ 100
- สีวงคะแนน: ≥75 เขียว · 50–74 เหลือง · <50 แดง; ข้อที่ไม่ตรงแสดงเด่นกว่าวงคะแนนเสมอ
- **สีรายข้อ** (`criterionTone()` ใน `apps/consumer-app/lib/lead-room-compare.ts`) ดูจาก % ของข้อนั้นที่แสดง (ปัดแล้ว) ไม่ใช่ชื่อสถานะ: 100 เขียว · 1–99 เหลือง · **0 แดง** · ไม่นับ “—” เทา — เช่น ประเภทห้อง/สัญญาไม่ตรง (0%) และ “ว่างช้ากว่า” เกินช่วงผ่อนผัน (0%) เป็นแดง ส่วนเกินรัศมีเล็กน้อยเป็นเหลือง ใช้ทั้ง % · pill · แถบซ้ายของแถวในหน้าเทียบห้อง และชิปเหตุผลบนการ์ดห้อง
- listing card ต้องมี `roomTypeCode`, `availableFromDate`, `prices[].termMonths` เพื่อให้การ์ดคิดได้ครบโดยไม่ต้องโหลดรายละเอียดห้อง

### การแสดงผล

- **การ์ดห้องใน Lead detail:** แสดงทีละ 10 ห้องเรียงคะแนนรวม (`MATCH_PAGE_SIZE`) มีปุ่ม “ดูเพิ่มอีก N ห้อง” เพิ่มทีละ 10 จนครบ (รีเซ็ตเป็น 10 เมื่อเปลี่ยนลีด/โหลด pool ใหม่) · หัวข้อ “ห้องที่จับคู่ (แสดงอยู่ จาก ทั้งหมด)” ระหว่างยังแสดงไม่ครบ แล้วเป็น “ห้องที่จับคู่ (N)” เมื่อครบ + คำอธิบาย “คัดกรองเบื้องต้น · อยู่ในงบ และห่างไม่เกิน 2 เท่าของรัศมี”; บนการ์ดแสดงเหตุผลที่ไม่ตรงสูงสุด 2 ข้อ (เช่น “ต้องการ 3 ห้องนอน · ห้องนี้สตูดิโอ”, “เกินรัศมีที่ตั้งไว้ 1.2 กม.”) + “+N ข้อที่ไม่ตรง”; ถ้าไม่มีข้อไม่ตรง แสดง “ผ่านทุกข้อที่ประเมินได้”
- **หน้าเทียบห้อง** (shell tab `leadRoom`) — เมื่อโหลด `GET /agent/listings/:id` แล้วคำนวณใหม่ด้วยข้อมูลห้องเต็ม:
  - **โครงหน้า:** 3 การ์ด (สรุป → ผลการประเมิน → ข้อมูลห้อง) เว้นระหว่างก้อน 20 · หัวข้อถึงการ์ด 8 · ขอบในการ์ด 16 · ปุ่ม “ดูห้องนี้” ติดล่างจอใน `bottomBar` ของ shell (`LeadMatchedRoomCta`) และยังอยู่ในเมนู ⋯
  - **การ์ดสรุป:** รูปห้องเป็นหัวการ์ด สูงไม่เกิน 180px (`min(width × 0.5, 180)`; โหลดห้องไม่ได้แสดงข้อความ + ลองใหม่ในพื้นที่รูป) · ชื่อโครงการ · บรรทัดรอง “ประเภทห้อง · ขนาด” (จากข้อมูลโครงสร้าง ไม่ใช้ข้อความโปรโมต) · ราคา + ระยะสัญญา · “เขต · X กม. จาก {ชื่อหมุด}” · วงคะแนนรวม · ท้ายการ์ด “ประเมินได้ X จาก 5 หัวข้อ” (X = ข้อที่มีคะแนน) และ “ไม่ตรง N ข้อ” เมื่อมี (แดงถ้ามีข้อที่ได้ 0% ไม่งั้นเหลือง) — ไม่มีแถวชิปแยก เพราะซ้ำกับตาราง
  - **ตารางเทียบ:** หัวคอลัมน์ “ลีดต้องการ | ห้องนี้” ครั้งเดียวบนการ์ด แล้วแถวละหัวข้อ เรียงคงที่ งบ → ทำเล → ประเภทห้อง → สัญญา → วันเข้าอยู่ (ทุกห้องเรียงเหมือนกัน)
  - แต่ละแถว: บรรทัดบน ไอคอน + หัวข้อ + % ของข้อนั้น (สีรายข้อ: 100 เขียว · 1–99 เหลือง · 0 แดง · ไม่นับ “—”) + pill สีเดียวกับ % เฉพาะข้อที่ไม่ตรง/ไม่นับ (“ไม่ตรง”, “เกินรัศมี”, “ห้องไม่ระบุ”, “รอยืนยัน”); บรรทัดล่าง ค่าลีด (สีรอง) | ค่าห้อง (สีหลัก) ตรงกับหัวคอลัมน์ · งบมี “ต่ำกว่างบ X ฿” ใต้ค่าห้องเมื่อมีส่วนต่าง · ไม่มีหลอดคะแนน
  - แถวที่ไม่ตรง: แถบ 3px ด้านซ้าย + พื้นจาง + ค่าห้องตัวหนา ตามสีรายข้อ (เหลือง: พื้น 8% · แดง: พื้น 7%)
  - หมายเหตุสีเทา: ทำเล <100 แสดงที่มา “ระยะ X% × หมุดอันดับ N (W%)” · ข้อที่ไม่นับ “· ไม่รวมในคะแนน”
  - โหมดมืดใช้โทนสถานะที่สว่างขึ้น (เขียว `#4ADE80`, เหลือง `#FBBF24`, แดง `#F87171`) แทนสี pastel ของโหมดสว่าง
  - **การ์ดข้อมูลห้อง:** แถว ป้ายซ้าย–ค่าขวา + ไอคอน แบ่ง 2 กลุ่ม — “ตัวห้อง” (ห้องนอน: 0 หรือประเภท studio แสดง “สตูดิโอ” ผ่าน `formatBedroomSpec` · ห้องน้ำ · ขนาด · ชั้น/อาคาร ใช้ข้อความ spec เดียวกับหน้ารายละเอียดห้อง) และ “ค่าใช้จ่าย (สัญญา N เดือน)” (เงินประกัน / ค่าเช่าล่วงหน้า เป็น “N เดือน · X ฿” จากราคาของระยะสัญญาที่จับคู่ ไม่มี = “ไม่มี” · เงินก้อนแรก = ประกัน + ล่วงหน้า ตัวหนา · ค่าน้ำ · ค่าไฟ); ข้อที่ห้องไม่มีข้อมูลซ่อนทั้งแถว ไม่แสดง 0 หรือ “—”
  - **“คะแนนนี้คิดอย่างไร”** แถวสุดท้ายในการ์ดตาราง (พับไว้ กางในการ์ด): คำอธิบายกลางๆ ใช้ได้ทุกห้อง ไม่มีตัวเลข/สูตร 3 ข้อ — ยิ่งตรงยิ่งสูง · แต่ละหัวข้อ 0–100% (ตรงเต็ม 100% ใกล้เคียงได้บางส่วน) · คะแนนรวม = ค่าเฉลี่ยของหัวข้อที่เทียบได้ “—” ไม่นำมาคิด; สูตรละเอียดอยู่ในชีต “เกณฑ์คะแนนจับคู่” ที่หน้า Lead detail
- **Accessibility:** วงคะแนนอ่านว่า “คะแนนความเหมาะสม N จาก 100” ตามด้วยข้อที่ไม่ตรง; แต่ละแถวอ่าน “{หัวข้อ} N จาก 100” หรือ “{หัวข้อ}, ไม่นับในคะแนน” ตามด้วยสถานะ ค่าที่ต้องการ/ค่าห้อง และหมายเหตุ
- **Lead ที่ `booked`** ไม่แสดงผลจับคู่
- เมื่อย้ายไป server ให้คง response shape ใกล้ `LeadRoomMatch` (`room`, `score`, `locationScore`, `price`, `termMonths`, `pin`, `distanceKm`, `withinRadius`, `comparison`) เพื่อสลับ data source ได้โดยไม่แก้ UI

## 6. สิ่งที่ยังไม่มีในระบบ

- [ ] API matching / คำนวณคะแนน (ตอนนี้เป็นผลเบื้องต้นฝั่ง client — §5.1) → แผนใน [match-settings.md](./match-settings.md)
- [ ] นิยาม hard filter query (SQL) ให้ชัด รวมกฎราคาเมื่อไม่ระบุระยะสัญญา
- [ ] JSON schema สำหรับ Gemini (lead preferences + room facts → qualitative score และเหตุผล)
- [ ] นโยบายห้อง (pets / smoking) ถ้าจะ hard-filter ได้จริง
- [x] UI แสดง shortlist + % match บน lead detail (ข้อมูลจาก §5.1)
- [ ] วันที่ย้ายเข้า/ความยืดหยุ่นแบบ structured แทน `move_in_plan` ข้อความอิสระ
- [ ] ระบุว่าเงื่อนไขไหน `must_have` และอันไหน `preference` โดยเฉพาะประเภทห้อง ทำเล สัตว์เลี้ยง และที่จอดรถ
- [ ] กำหนดความยืดหยุ่นของงบ/พื้นที่จาก Lead เพื่อแสดงผล “ใกล้เคียง” แยกจากผล match ตรง
- [ ] ข้อมูลห้องที่ยังไม่มีคู่เทียบ: pet/smoking/parking policy, max occupants; แยก `unknown` จาก `not_allowed`
- [ ] สูตรคะแนนที่ versioned, confidence, no-match fallback, ชุดตัวอย่างสำหรับประเมิน และ cache invalidation
- [ ] จำกัดข้อมูลส่งให้ AI + schema validation + fallback เมื่อ AI ใช้งานไม่ได้
