# ตรวจ flow Agent: จองห้อง → สัญญาเช่า → ต่อสัญญา

การตรวจครั้งแรกวันที่ 12 ตุลาคม 2026 ตามเวลา Asia/Bangkok รวมงานต่อสัญญาที่ยังไม่ commit โดยยังไม่แก้โค้ดในรอบตรวจ; รายการด้านล่างเก็บเป็นบันทึกก่อนแก้ อ่านสถานะล่าสุดได้จากส่วนถัดไป

## สถานะหลังแก้ — 12 ตุลาคม 2026

แก้ข้อบกพร่องทั้ง 7 จุดแล้ว และเพิ่ม regression tests โดยรักษางานที่แก้ค้างอยู่ก่อนหน้า ไม่ได้ deploy หรือเปลี่ยนข้อมูลฐานข้อมูลจริง

- หน้ารวมตรวจสิทธิ์ต่อสัญญาแยกตามสายสัญญา เมื่อหลายผู้เช่าต่อได้ ให้เลือกผู้เช่า/ห้องและฉบับต้นทางก่อน
- การเปิดฟอร์มจากหน้าผู้เช่ารอโหลดรายการสัญญาให้เสร็จ เพื่อไม่ตรวจสิทธิ์จากรายการว่าง
- API กันช่วงทับระหว่าง lease และ renewal ทั้งสองทิศทาง; reservation/broker appointment ยังอยู่ร่วมได้
- ซ่อนงานต่อสัญญาของ predecessor เมื่อมี successor ที่ไม่ถูกยกเลิก การยกเลิกร่างทำให้งานกลับมาได้
- daysLeft/progress/current lease ใช้ calendar date ของ Asia/Bangkok
- UI/API ปฏิเสธวันที่ไม่มีจริง และ API ตรวจ operational fields ซ้ำหลังรวม overlay รวมถึงทศนิยมเงิน
- เลข/วันที่/วันหมดอายุของ predecessor ถูกกำหนดจากระบบ ช่องเลขและวันที่สัญญาเดิมในฟอร์มถูกล็อก
- บิลถัดไปเลือกวันออกบิลที่ถึงก่อนจากทุกห้อง และตัดเฉพาะ predecessor ที่ renewal เริ่มมีผลแล้ว
- กติกาใหม่สำหรับสิ้นเดือน: หากเดือนปลายทางไม่มีวันครบรอบ ให้จบวันสุดท้ายของเดือนนั้น เริ่ม 31/01/2026 ต่อ 1 เดือนจบ 28/02/2026; เริ่ม 29/02/2024 ต่อ 12 เดือนจบ 28/02/2025
- เส้นทางต่อด้วย full lease เดิมใช้ขอบเขตล่วงหน้า 30 วันเหมือนหนังสือต่อสัญญาแล้ว แต่ยังรองรับวันเริ่มที่มีช่องว่างตามพฤติกรรมเดิมของสัญญาเช่าเต็มฉบับ

ผลตรวจหลังแก้:

- ชุด contract/tenant/billing และ tests ฝั่ง consumer ทั้ง helpers/components รวม public signing: **213/213 ผ่าน**
- Regression runner เฉพาะส่วนที่เกี่ยวข้อง: **38/38 ผ่าน** รันด้วย `node tmp/contract-flow-audit-2026-10-12.cjs`

## Flow ที่ตรวจครั้งแรก (ก่อนแก้)

| ขั้นตอน | พฤติกรรมที่พบ |
| --- | --- |
| จองห้องจาก Lead | ล็อก Lead และห้อง สร้าง Tenant และเปลี่ยน Lead เป็น `booked` กัน Lead จองห้องซ้ำ |
| สร้างหนังสือจอง | ใช้ Lead ที่จองแล้ว สร้าง draft, occupancy แบบ `prospect` และใบแจ้งหนี้เงินจอง |
| ชำระเงินจอง | ผู้เช่าส่งหลักฐาน Agent ออกใบเสร็จ ผู้เช่าจึงลงนามได้ หลักฐานส่งอย่างเดียวยังไม่ถือว่าจ่ายแล้ว |
| ลงนามหนังสือจอง | ต้องมีเจ้าของ ผู้เช่า และ Agent ครบ แล้วสร้าง PDF ฉบับลงนามจึงเป็น `active` |
| สร้างสัญญาเช่า | ต้องมีหนังสือจองฉบับสมบูรณ์ก่อน ตั้งวัน/ค่าเช่า/เงินประกัน ลงนามเจ้าของและผู้เช่า แล้ว Agent สร้าง PDF |
| เปิดต่อสัญญา | ฉบับเดิมต้องเป็น lease/renewal ที่ `active` หรือ `expired` มีวันสิ้นสุดและไม่มี successor ที่ไม่ถูกยกเลิก |
| ต่อสัญญาล่วงหน้า | API หนังสือต่อสัญญาเปิดตั้งแต่วันสิ้นสุดเดิมลบ 30 วัน ฉบับใหม่เริ่มวันสิ้นสุดเดิมบวก 1 วัน |
| ลงนาม/ออกเอกสารต่อสัญญา | ใช้ลายเซ็นใหม่ของเจ้าของและผู้เช่า เก็บ previous/root ของสายสัญญาเดิม |
| บิลหลังต่อสัญญา | หนังสือต่อสัญญารองรับบิลแล้ว ตัวกรองหยุดใช้ predecessor เมื่อถึงวันเริ่ม successor; วันออกบิลล่วงหน้าอาจอยู่ก่อนวันเริ่มสัญญาตามกติกาออกบิล 5 วัน |

## ข้อบกพร่องที่ยืนยันได้ก่อนแก้

### 1. P1 — หน้ารวมใช้สัญญาของผู้เช่าคนอื่นตัดสินว่าต่อได้หรือไม่

[renewalTail](/Users/jsr/NESTYK/apps/consumer-app/components/ContractsScreen.tsx:149) เลือกฉบับที่วันสิ้นสุดไกลที่สุดจาก `contracts` ทั้งหมด และ [ปุ่มต่อสัญญา](/Users/jsr/NESTYK/apps/consumer-app/components/ContractsScreen.tsx:2380) แสดงเฉพาะฉบับนั้น หน้ารวมโหลดสัญญาทั้ง Agent เมื่อไม่มี prop `tenant`

ตัวอย่างวันนี้ 12/10/2026: ผู้เช่า A หมด 31/10/2026 จึงต่อได้แล้ว แต่ผู้เช่า B หมด 30/06/2027 ทำให้เลือก B และแจ้งว่ายังต่อเร็วเกินไป ปุ่มของ A ไม่แสดง ข้อผิดพลาดนี้ไม่เกิดเมื่อรายการถูกจำกัดเฉพาะผู้เช่า A

ควรหาฉบับล่าสุดแยกตามสายสัญญา/ผู้เช่า/ห้อง ตรวจฉบับที่เลือกโดยตรง และให้เลือกสัญญาต้นทางในหน้าสร้างจากรายการรวม

### 2. P1 — สัญญาเช่าและหนังสือต่อสัญญาทับช่วงกันได้

[overlap query](/Users/jsr/NESTYK/apps/api/src/agent/contracts/agent-contracts.service.ts:3000) กันเฉพาะ `form_kind` เดียวกัน ดังนั้น `lease` และ `renewal` ไม่ตรวจชนกัน แม้เป็นสิทธิ์เช่าห้องเดียวกัน

ตัวอย่างมี lease เดิมหมด 31/10/2026 และสร้าง lease ใหม่ช่วง 01/11/2026–31/10/2027 แบบไม่อ้าง previous ไว้แล้ว จากนั้นสร้าง renewal ของฉบับเดิมช่วงเดียวกัน API ยอมรับ เพราะ lease ใหม่ไม่ใช่ successor และถูกตัดออกจาก overlap query อาจเกิดสองสัญญาและสองชุดบิล

ยืนยันด้วย service fixture ที่เรียก `saveDraft` จริงและจำลองตัวกรอง query; ยังไม่ได้รันเคสนี้กับ PostgreSQL จริง ควรตรวจ lease/renewal เป็นกลุ่มเดียวกัน แต่ยังอนุญาต reservation และ broker appointment อยู่ร่วมได้

### 3. P2 — ต่อสัญญาล่วงหน้าเสร็จแล้ว แต่รายการงานยังแจ้งให้ต่อฉบับเดิม

[tenantWorkItems](/Users/jsr/NESTYK/apps/consumer-app/lib/tenant-work.ts:54) ตรวจ daysLeft ของฉบับที่ครอบคลุมวันนี้โดยไม่ตรวจ successor

ตัวอย่าง lease หมด 31/10/2026 และ renewal 01/11/2026–31/10/2027 เป็น `active` แล้ว วันที่ 12/10/2026 ยังขึ้นงานต่อสัญญาของ lease เดิม เมื่อเปิดฟอร์มกลับต่อซ้ำไม่ได้

ควรซ่อนงานต่ออายุเมื่อมี successor ที่ไม่ถูกยกเลิก และแสดงงานร่าง/ลงนาม/ออกเอกสารของ successor หากยังไม่สมบูรณ์

### 4. P2 — จำนวนวันคงเหลือใช้ timezone ของเครื่อง แต่หน้าต่อสัญญาใช้กรุงเทพฯ

[dateKey](/Users/jsr/NESTYK/apps/consumer-app/lib/tenant-detail.ts:8) ใช้ `getFullYear/getMonth/getDate` ตาม timezone เครื่อง ขณะที่ renewal gate และ API ใช้ Asia/Bangkok

ที่เวลา 01/10/2026 00:30 กรุงเทพฯ (30/09/2026 17:30 UTC) เครื่องที่ตั้ง UTC จะแสดงเหลือ 31 วันและไม่แสดงงานต่ออายุ แต่ฟอร์ม/API เปิดให้ต่อแล้วเพราะเหลือ 30 วันตามกรุงเทพฯ ยืนยันด้วยเคสจำลอง timezone UTC

ควรใช้ calendar date ของ Asia/Bangkok เดียวกันสำหรับ daysLeft, progress และการเลือก current lease

### 5. P2 — วันที่จัดทำ/วันที่อ้างอิงที่ไม่มีจริงผ่าน validation ได้

[dateField](/Users/jsr/NESTYK/apps/api/src/agent/contracts/lease-renewal.ts:47) ตรวจ pattern และ `Date.parse` แต่ไม่ตรวจวันที่ย้อนกลับ JavaScript แปลง `2026-02-30` เป็นวันในเดือนมีนาคม จึงไม่เป็น NaN ค่า issueDate นี้ยังถูกเก็บใน JSON และส่งไปพิมพ์ PDF ตามข้อความเดิม

ฝั่ง lease overlay ก็ตรวจวันเพียง pattern และแทนที่วันที่ที่ top-level เคย validate แล้ว หาก API รับ top-level วันที่ถูกต้องแต่ `leaseAgreement.termFrom = 2026-02-30` service จะส่งวันที่ผิดไปเขียนคอลัมน์ DATE ซึ่ง PostgreSQL จะปฏิเสธแทนการตอบ validation ที่ชัดเจน จุดนี้ยืนยันได้ถึงข้อมูลที่ส่งเข้า save จาก fixture ไม่ได้ยืนยันการเขียนลง DB สำเร็จ

ควรใช้ validator วันจริงร่วมกัน และ validate operational fields อีกรอบหลังรวม overlay

### 6. P2 — หนังสือต่อสัญญาอ้างเลข/วันที่สัญญาเดิมผิดได้

[การตรวจ predecessor และเติม root](/Users/jsr/NESTYK/apps/api/src/agent/contracts/agent-contracts.service.ts:2867) ตรวจสิทธิ์ ความสัมพันธ์ และวันเริ่ม แต่เติมจากระบบเฉพาะ `firstLease*` โดยไม่ตรึง `originalLeaseNo/originalLeaseDate` ให้ตรงกับ predecessor ที่เลือก ช่องสองช่องนี้แก้ได้ในฟอร์ม

ทดสอบส่ง `originalLeaseNo = UNRELATED-CONTRACT` ร่วมกับ previousAgreementId ที่ถูกต้อง พบ service รับและเก็บข้อความผิด เอกสารจึงอ้างสัญญาคนละฉบับกับ lineage ในฐานข้อมูล

ควรดึงเลข/วันที่จัดทำของ predecessor จากระบบและล็อกสองช่องในฟอร์ม

### 7. P2 — บิลถัดไปของผู้เช่าหลายห้องเลือกตามวันเริ่มสัญญา ไม่ใช่บิลที่ถึงก่อน

[upcomingTenantBill](/Users/jsr/NESTYK/apps/consumer-app/lib/tenant-bill-upcoming.ts:16) เลือกสัญญาที่เริ่มล่าสุดก่อนการเรียงวันออกบิล ทำให้สัญญาของอีกห้องที่มีบิลถึงก่อนถูกมองข้าม

ตัวอย่างห้อง A เริ่ม 01/01/2026 บิลออก 15/10/2026; ห้อง B เริ่ม 01/10/2026 บิลออก 01/11/2026 ฟังก์ชันเลือก B ยืนยันด้วยข้อมูลที่มี startDate ครบตาม DTO จริง

ควรตัด predecessor ที่ถูกต่อแล้วแยกตาม lineage ก่อน แล้วเลือกวันออกบิลเร็วที่สุดจากทุกห้องที่เหลือ
