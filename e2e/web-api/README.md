# ชุดเทส E2E ของ NESTYK: API และเว็บ (Playwright)

ชุดเทสนี้เรียกระบบที่รันอยู่จริงจากภายนอก เหมือนที่แอปมือถือและเว็บเรียก ตอนนี้มีเทส API ของ `apps/api` ซึ่งไม่สร้างและไม่แก้ข้อมูล (ดูข้อตกลงด้านล่าง) และเทสนำร่องที่เขียนข้อมูลจริงซึ่งแยกไว้ใน `tests/write` รันด้วยคำสั่งของตัวเองเท่านั้น (ดูหัวข้อ "เทสที่เขียนข้อมูล") เทสหน้าเว็บจะเพิ่มในขั้นถัดไป

โฟลเดอร์นี้มี `package.json` ของตัวเอง และไม่อยู่ใน workspaces ของ monorepo การติดตั้งที่นี่จึงไม่แตะ `package-lock.json` ของราก

ก่อนเริ่มเทส `src/global-setup.ts` ตรวจ 5 อย่างตามลำดับ ถ้าไม่ผ่านจะหยุดทั้งชุดและบอกสาเหตุ: API ตอบที่ `/health`, ตั้ง uuid ของ `qa-agent` แล้ว, บัญชี QA ทุกบัญชีที่ตั้ง uuid ไว้ (รูปแบบ uuid ถูก ไม่ซ้ำกัน API รับบัตรผ่านแบบนักพัฒนา มีในตาราง `users` อีเมลตรงกับบทบาท และบทบาทตรงกับ migration ทุกตัว แล้วพิมพ์บรรทัด `[บัญชี QA] ตรวจแล้ว N จาก 5 บัญชี` บอกว่าบัญชีไหนไม่ได้ตั้ง), `GET /agent/leads` ของ qa-agent ได้ 200 (ไม่ใช่ 5xx) และ API มีตัวตรวจ id ของรุ่น `f7d52ed` (id ที่เกินช่วงได้ 400 พร้อมข้อความที่ชุดเทสคาด) global-setup ไม่ได้นับลีดและห้องของ qa-agent ส่วนข้ออื่นข้างบนชุดเทสไม่ได้ตรวจ ต้องตรวจเองก่อนรัน เช่น `npm run db:check -w @nestyk/api -- --check` ต้องได้ ✓ และ 2 คำสั่งนี้ต้องไม่มีผลลัพธ์ ซึ่งแปลว่าโค้ดนอก `e2e/` บนเครื่อง รวมไฟล์ที่แก้ค้างและไฟล์ใหม่ที่ยังไม่ commit เหมือน develop (รันจากโฟลเดอร์ไหนใน repo ก็ได้ `origin/develop` คือ develop ตอน fetch ครั้งล่าสุด จึงควร fetch ก่อน)

## ข้อตกลงของชุดเทส

- ชื่อเทสเป็นภาษาอังกฤษ คอมเมนต์เป็นภาษาไทย
- ไฟล์เทสไม่ส่งคำขอ HTTP เอง ให้เรียกผ่านตัวเรียกใน `src/api/` (หลักเดียวกับ Page Object: ถ้าเส้นทางของ API เปลี่ยน แก้ที่เดียว)
- ตัวเรียกใน `src/api/` คืนคำตอบดิบและไม่ตรวจผล การตรวจอยู่ในไฟล์เทส เทสจึงตรวจได้ทั้งกรณีสำเร็จและกรณีที่ API ต้องปฏิเสธ
- เทสไม่ผูกกับจำนวนข้อมูลที่แน่นอน (เช่น ไม่ตรวจว่ามี 30 ห้อง) แต่ต้องมีลีดและห้องของ qa-agent อย่างน้อยตามที่บอกในหัวข้อ "สิ่งที่ต้องมีก่อนรัน"
- เทสใน `tests/api` ไม่สร้างและไม่แก้ข้อมูล จึงรันพร้อมกันได้ เทสที่สร้างหรือแก้ข้อมูลอยู่ใน `tests/write` เท่านั้น และต้องทำตามกติกาในหัวข้อ "เทสที่เขียนข้อมูล" (ป้าย `E2E-` ชุดข้อมูลถาวรของสิ่งที่ลบไม่ได้ เก็บกวาด และตัวนับรอย)

## ยังไม่ครอบคลุม

- เทสที่สร้างหรือแก้ข้อมูล: `tests/write` มีเทสนำร่องของลีด (แก้ notes และเปลี่ยนสถานะลีดถาวร) และเทสวงจรเช่าห้องที่เดินเส้นทางปกติ 1 เส้นทาง (สร้างห้อง นัด ข้อเสนอ ผู้เช่า สัญญา 3 ฉบับ สลิปและใบเสร็จ ส่งมอบ บิล 1 ใบ แจ้งย้ายออก คืนมัดจำ) ยังไม่ได้เทสกรณีที่ต้องถูกปฏิเสธของเส้นทางเหล่านี้ ค่าอื่นของแต่ละฟอร์ม การตีกลับสลิป ค่าปรับจ่ายช้า ไม่ต่อสัญญา ต่อสัญญา ลิงก์แชร์ และจับคู่ห้อง
- การกันสิทธิ์ตามบทบาท: `roles.spec.ts` (ใช้บัญชี QA) ตรวจ 403 ของเส้นทาง GET ตัวแทนของทุก controller (รวมกลุ่มห้อง ลิงก์แชร์ จับคู่ห้อง และนัดดูห้อง) การเลือกเส้นทางตัวแทนพึ่งการที่ทุก controller ตั้ง `@Roles` ระดับ class `party-contracts.controller.ts` มี `@Roles('landlord')` ระดับ method: `GET mine/deal-offers` กับ `POST mine/deal-offers/:id/confirm` (ตั้งแต่ develop `f845ac6`) และ `GET mine/reminders` (ตั้งแต่ develop `8a62e39`) และ RolesGuard ใช้ค่าระดับ method แทนระดับ class (`getAllAndOverride`) ทั้ง 3 เส้นทางนี้จึงตรวจแยกในกลุ่ม "landlord contract routes" ถ้าทีมเพิ่ม `@Roles` ระดับ method ให้เส้นทางอื่นอีก เทสจะจับไม่ได้ และไม่ตรวจ 403 ของเส้นทาง POST/PUT/PATCH/DELETE (ถ้าบทบาทถูกคำขอจะบันทึกจริง) ยกเว้น `POST mine/deal-offers/:id/confirm` ซึ่งส่งเนื้อคำขอว่างที่ service ปฏิเสธด้วย 400 ก่อนแตะฐานข้อมูล ถ้าไม่ได้ตั้ง uuid ของบัญชี QA บัญชีไหน เทสที่ใช้บัญชีนั้นข้าม
- กลุ่มผู้เช่าและสัญญา: เส้นทางปกติของการสร้างผู้เช่าและสัญญา 3 ฉบับ การออกเอกสาร และการลงนาม มีเทสใน `tests/write/rental-lifecycle.write.spec.ts` แล้ว ยังไม่ได้เทสการกันข้อมูลข้ามนายหน้าหรือข้ามคู่สัญญา และกรณีที่ต้องถูกปฏิเสธ (ต้องสร้างข้อมูลก่อน) เส้นทาง POST, PUT และ DELETE ของสัญญาฝั่งนายหน้าที่มีเทส คือ `deposit-invoice`, `witness-sign` และ 12 เส้นทางของ develop `9644dd9` (เลิกสัญญาก่อนกำหนด ไม่ต่อสัญญา บันทึกย้ายออก รายการหักและการคืนเงินประกัน) ทุกข้อเทสแค่สัญญาที่ไม่มีอยู่จริง ส่วนที่เหลือยังไม่ได้เทส
