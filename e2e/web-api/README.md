# ชุดเทส E2E ของ NESTYK: API และเว็บ (Playwright)

ชุดเทสนี้เรียกระบบที่รันอยู่จริงจากภายนอก เหมือนที่แอปมือถือและเว็บเรียก ตอนนี้มีเทส API ของ `apps/api` ซึ่งไม่สร้างและไม่แก้ข้อมูล (ดูข้อตกลงด้านล่าง) และเทสนำร่องที่เขียนข้อมูลจริงซึ่งแยกไว้ใน `tests/write` รันด้วยคำสั่งของตัวเองเท่านั้น (ดูหัวข้อ "เทสที่เขียนข้อมูล") และเทส UI ของเว็บ consumer-app ใน `tests/web-ui` ซึ่งรันด้วยคำสั่งของตัวเองเช่นกัน (ดูหัวข้อ "เทส UI เว็บ consumer-app")

โฟลเดอร์นี้มี `package.json` ของตัวเอง และไม่อยู่ใน workspaces ของ monorepo การติดตั้งที่นี่จึงไม่แตะ `package-lock.json` ของราก

## ข้อตกลงของชุดเทส

- ชื่อเทสเป็นภาษาอังกฤษ คอมเมนต์เป็นภาษาไทย
- ไฟล์เทสไม่ส่งคำขอ HTTP เอง ให้เรียกผ่านตัวเรียกใน `src/api/` (หลักเดียวกับ Page Object: ถ้าเส้นทางของ API เปลี่ยน แก้ที่เดียว)
- ตัวเรียกใน `src/api/` คืนคำตอบดิบและไม่ตรวจผล การตรวจอยู่ในไฟล์เทส เทสจึงตรวจได้ทั้งกรณีสำเร็จและกรณีที่ API ต้องปฏิเสธ
- เทสไม่ผูกกับจำนวนข้อมูลที่แน่นอน (เช่น ไม่ตรวจว่ามี 30 ห้อง) แต่ต้องมีลีดและห้องของ qa-agent อย่างน้อยตามที่บอกในหัวข้อ "สิ่งที่ต้องมีก่อนรัน"
- เทสใน `tests/api` ไม่สร้างและไม่แก้ข้อมูล จึงรันพร้อมกันได้ เทสที่สร้างหรือแก้ข้อมูลอยู่ใน `tests/write` (ผ่าน API) และ `tests/web-ui-write` (ผ่านหน้าเว็บ) เท่านั้น และต้องทำตามกติกาในหัวข้อ "เทสที่เขียนข้อมูล" (ป้าย `E2E-` ชุดข้อมูลถาวรของสิ่งที่ลบไม่ได้ เก็บกวาด และตัวนับรอย)
- เทสของเส้นทางที่บันทึกข้อมูล (POST, PUT, PATCH และ DELETE ของผู้เช่า สัญญา และบิล) ส่งเฉพาะคำขอที่ระบบต้องปฏิเสธ และใช้ id ที่ไม่มีอยู่จริง (2147483647) ถ้าคำขอผ่านการตรวจค่าไปได้ ระบบจะหาข้อมูลไม่เจอแล้วตอบ 404 ก่อนบันทึก (ตรวจลำดับนี้ในโค้ดของ API ที่ qa/e2e `4833ace` (develop `b228ee3`) แล้วทุกเส้นทางของผู้เช่าและสัญญาที่เทส ส่วนกลุ่ม `bills/*` และเส้นทางที่เพิ่มใน develop `9644dd9` ตรวจที่ `9644dd9` ส่วน `early-end` กับ `not-renewing` ซึ่งทีมแก้ใน `1b16d32` ตรวจซ้ำที่ `bc77a8b`)
  - `POST /agent/contracts/:id/witness-sign` ตรวจชื่อพยานและลายเซ็นก่อนหาสัญญา เทส 404 จึงส่งภาพลายเซ็น PNG ที่อ่านได้ไปด้วย
  - เส้นทางลงนามผ่านลิงก์แบบไม่ต้องล็อกอิน (`/public/contract-sign/:token`) ทีมลบแล้วใน develop `b228ee3` เทสตรวจว่าเปิดไม่ได้แล้ว (NestJS ตอบว่าไม่มีเส้นทางนี้)
  - เส้นทางที่เจ้าของห้องออกใบค่าปรับ (`POST bills/received/:id/late-fee`) ทีมลบแล้วใน develop `1b16d32` เทสตรวจว่าเปิดไม่ได้แล้วโดยเรียกแบบไม่ล็อกอิน (NestJS ตอบว่าไม่มีเส้นทางนี้)
  - ห้อง ลิงก์แชร์ จับคู่ห้อง และนัดดูห้อง (`agent-rooms.spec.ts`, `share-links.spec.ts`, `lead-matching.spec.ts`, `lead-viewings.spec.ts`): บางข้อส่งไปที่ห้องหรือลีดจริงของ qa-agent ด้วยค่าที่ตัวตรวจปฏิเสธก่อนบันทึก (ลำดับการตรวจอ้างบรรทัดในหัวไฟล์เทสและตัวเรียก ที่ develop `bc77a8b`) แล้วอ่านซ้ำว่าข้อมูลเท่าเดิม (จำนวนลิงก์ ค่าตั้งการจับคู่ ผลจับคู่ล่าสุด นัดของลีด) ก่อนตรวจรหัสตอบกลับ ถ้าไม่เท่า เทสไม่ผ่านพร้อมข้อความ "ให้แจ้งทีม" และ id ของห้องหรือลีด (ไม่พิมพ์เนื้อคำตอบของการสร้างลิงก์ เพราะมี token จริง) เนื้อคำขอส่วนใหญ่ผิด 2 จุด จึงถูกกันได้ 2 ด่าน ข้อที่มีด่านเดียวเขียนไว้ในหัวไฟล์เทสว่าเป็นความเสี่ยงที่เหลือ (POST match-runs ของลีดที่ไม่พร้อม 422 ไม่อยู่ในชุดนี้ เพราะถ้าตัวตรวจความพร้อมหาย จะบันทึกการจับคู่และอาจลบรอบเก่าที่ย้อนไม่ได้ ดูหัวไฟล์ `lead-matching.spec.ts`) ไม่ส่งรูปจริงไปเส้นทางอัปโหลด และไม่ส่ง `listing` ที่เป็น object ไปเส้นทางสร้างข้อความโปรโมต (เรียก Gemini ซึ่งมีค่าใช้จ่าย)
- `POST /auth/dev/roles` บันทึกบทบาทให้บัญชีทันทีถ้าชื่อบทบาทอยู่ในรายการที่ขอได้และมีแถวใน `master_roles` เทสส่งแค่ชื่อที่ไม่มีอยู่จริงกับชื่อ owner ที่เลิกใช้แล้ว ซึ่ง `grantDevRole` ปฏิเสธก่อนอ่านตารางบทบาท (`apps/api/src/auth/auth.service.ts:166-172` ที่ develop `84087e2`)
  - ก่อนส่งชื่อ owner เทสตรวจว่าบัญชีมี landlord ไม่มี owner และดูรายการบทบาทที่ขอได้จากคำตอบของชื่อที่ไม่มีอยู่จริง ถ้ารายการยังมี owner (API รุ่นก่อน 84087e2) เทสจะหยุดก่อนส่ง
- รายงาน HTML (`playwright-report/`, `playwright-report-write/`) บันทึกข้อความของทุกการตรวจเป็นขั้น แม้การตรวจจะผ่าน และบันทึกที่อยู่ (path) ของทุกคำขอที่ส่งด้วยตัวส่งคำขอของ Playwright
  - `expectJson`, `expectError`, `expectCodedError` (`src/support/http.ts`) และ `expectSameAsNonexistent` (`src/support/cross-agent.ts`) จึงใส่ที่อยู่และเนื้อคำตอบในข้อความเฉพาะตอนรหัสไม่ตรง (ก่อน 3 พ.ย. 2026 ใส่ทุกครั้ง: ห้องทดลองนับรายงานของ `npm test` 1 รอบได้ 692 ขั้นที่มีที่อยู่และเนื้อคำตอบ 500 ตัวอักษร)
  - ไฟล์ใน Storage (รูปโปรไฟล์) และหน้าแชร์ (มี token ในที่อยู่) เปิดด้วย `fetch` ของ Node (`PublicFileApi`, `PublicRoomShareApi`) ซึ่งไม่ถูกบันทึกในรายงาน
  - คำค้นที่ส่งเป็น query (`params` ใน `src/api/api-client.ts`) เช่น `q` ของ owner-users, leads และ listings ไม่อยู่ในขั้นของคำขอ (ห้องทดลอง 3 พ.ย. 2026 ที่ Playwright 1.63 ไม่เปิด trace: ค้นทั้งรายงานแล้วไม่พบอีเมลหรือเบอร์ที่ใช้ค้น และพบ `q=` เฉพาะเส้นทางที่เทสพิมพ์ `?q=a&q=b` ไว้ในที่อยู่เอง) แต่ id ที่อยู่ในที่อยู่ เช่น `agent/leads/94` อยู่ในรายงาน และข้อที่ไม่ผ่านผ่าน `expectJson` จะมีที่อยู่เต็มรวม query
  - ข้อที่ไม่ผ่าน รวมข้อ `@known-bug` ที่ล้มตามคาดทุกรอบ ยังมีที่อยู่และเนื้อคำตอบของข้อนั้นในรายงาน (ตั้งใจ เพื่อดูสาเหตุ) รายงานของทุกรอบจึงมีขั้นแบบนี้อย่างน้อย 1 ขั้น

ตั้ง uuid ของบัญชี QA ใน Terminal ก่อนรัน: **ใส่คำสั่งข้างล่างทีละบรรทัด** (อย่าวางทั้งก้อน เพราะ bash รุ่นเก่าจะเอาบรรทัดถัดไปเป็นคำตอบของ `read`) แล้ววาง UID เมื่อถูกถาม (ตัวอักษรไม่ขึ้นบนจอ)
อย่าพิมพ์ UID ไว้ในคำสั่ง `export` ตรง ๆ เพราะ Terminal (zsh ของ macOS) เก็บคำสั่งที่พิมพ์ลงไฟล์ประวัติ (`~/.zsh_history`) ส่วน `read` ไม่ถูกเก็บ
ค่าอยู่แค่ใน Terminal หน้าต่างนั้น ปิดหน้าต่างแล้วต้องตั้งใหม่ ก่อนอ่านผล ให้ดูบรรทัด `[บัญชี QA] ตรวจแล้ว N จาก 5 บัญชี` ว่า N ตรงกับจำนวนที่ตั้ง (ถ้าตั้งแค่ qa-agent เทสสิทธิ์ส่วนใหญ่และเทสของ qa-tenant กับ qa-landlord จะข้าม แม้ผลรวมจะเขียว) และดูบรรทัด `นายหน้าคนที่ 2` กับ `คู่สัญญาของเทสวงจรเช่าห้อง` ว่าขึ้น "ตรวจแล้ว" ตามที่ตั้ง

```bash
printf 'UID ของ qa-guest: ';    read -rs E2E_QA_GUEST_UUID;    echo
printf 'UID ของ qa-tenant: ';   read -rs E2E_QA_TENANT_UUID;   echo
printf 'UID ของ qa-landlord: '; read -rs E2E_QA_LANDLORD_UUID; echo
printf 'UID ของ qa-agent: ';    read -rs E2E_QA_AGENT_UUID;    echo
printf 'UID ของ qa-admin: ';    read -rs E2E_QA_ADMIN_UUID;    echo
printf 'UID ของ qa-agent2: ';   read -rs E2E_QA_AGENT2_UUID;   echo
printf 'UID ของ qa-e2e-tenant: ';   read -rs E2E_QA_E2E_TENANT_UUID;   echo
printf 'UID ของ qa-e2e-landlord: '; read -rs E2E_QA_E2E_LANDLORD_UUID; echo
export E2E_QA_GUEST_UUID E2E_QA_TENANT_UUID E2E_QA_LANDLORD_UUID E2E_QA_AGENT_UUID E2E_QA_ADMIN_UUID E2E_QA_AGENT2_UUID E2E_QA_E2E_TENANT_UUID E2E_QA_E2E_LANDLORD_UUID
npm test
```

บัญชีที่ยังไม่มี UID ให้กด Enter ข้ามไป (ค่าว่าง = ไม่ได้ตั้ง เทสของบัญชีนั้นจะข้าม) ยกเว้น qa-agent ซึ่งต้องมีทุกครั้ง

ถ้าทีมเปลี่ยนรายการบทบาทของ `agent/leads/*` หรือ `contracts/mine*` (2 กลุ่มที่ global-setup ใช้ยืนยันว่าบัญชี QA มีอยู่) ชุดเทสจะหยุดทั้งชุดที่ global-setup พร้อมข้อความบอกเส้นทาง แทนที่จะเห็นเป็นเทสที่ล้มรายข้อ ตั้งใจให้หยุดก่อนเรียก `POST /auth/sync`

### สิ่งที่ต้องมีก่อนรัน

- เว็บเปิดอยู่: `cd apps/consumer-app && npm run web` และเว็บต้องเรียก API ของ staging (`EXPO_PUBLIC_API_URL` ใน `.env` ชี้ `nestyk-dev.up.railway.app`) **ห้ามรันชุดนี้วันที่ให้เว็บเรียก API บนเครื่อง** (ดู "กฎความปลอดภัย") ยกเว้นทำตามหัวข้อ "ใช้ API บนเครื่อง" ด้านล่างครบทุกข้อ

- รหัสผ่านของบัญชี QA ตั้งเป็นตัวแปรแวดล้อมในหน้าต่าง Terminal ที่จะรัน ด้วย `read -s` เพื่อไม่ให้รหัสค้างใน history ของ shell และห้ามเขียนลงไฟล์ รันเสร็จแล้วให้ล้างด้วย `unset`

read -s E2E_QA_TENANT_PASSWORD && export E2E_QA_TENANT_PASSWORD

# หลังรันเสร็จ

   - ทุกบัญชีที่ตั้งรหัสผ่านต้องมีในตาราง users แล้ว (ใช้ `checkQaAccount` ของชุด API: อ่านอย่างเดียวก่อน แล้วจึงเรียก `POST /auth/sync`) เพราะการล็อกอินบนเว็บเรียก sync ซึ่งจะสร้างผู้ใช้ใหม่ถ้าบัญชียังไม่มี
   - ผลอื่นทุกแบบ (400, 401, เครือข่ายล้ม) หยุดทั้งชุดพร้อมบอกสาเหตุ

### กฎความปลอดภัย

แอปขอบทบาทให้ตัวเองผ่าน `POST /auth/dev/roles` 2 จุด (บั๊กข้อ 1): ขอ agent เมื่อเปิดหน้า `/agent/...` ด้วยบัญชีที่ไม่ใช่นายหน้า (`apps/consumer-app/lib/agent-session.ts:72-76`) และขอ admin ทุกครั้งที่ล็อกอิน (`lib/auth/AuthContext.tsx:81-91`) ที่ qa/e2e `648dd28` ทั้ง 2 จุดขอเฉพาะ dev build ที่ตั้ง `EXPO_PUBLIC_ALLOW_DEV_ROLE_GRANT=true` (ไม่ตั้ง = ไม่ขอ เดิมจุดขอ admin ขอเว้นแต่ตั้ง `false` และจุดขอ agent ไม่ดูสวิตช์นี้) ผลรัน 6 พ.ย. 2026 ยังเห็นคำขอทั้ง 2 จุด แปลว่าเว็บที่ใช้รันวันนั้นตั้งค่านี้เป็น `true` (อนุมานจากโค้ด ไม่ได้อ่าน `.env`) API บนเครื่อง QA ตั้ง `ALLOW_DEV_ROLE_GRANT=true` และต่อฐานข้อมูลของทีม ถ้าคำขอนี้ถึง API บนเครื่อง บทบาทจะถูกบันทึกถาวร ชุดเทสจึงมีตัวกัน 3 ชั้น (`src/web-ui/guard.ts`)

1. คำขอ `/auth/dev/roles` ถูกตัดในเบราว์เซอร์ทุกครั้ง ไม่ว่าจะไป API ตัวไหน เทส known-bug ของข้อ 1 ใช้คำขอที่ถูกตัดนี้เป็นหลักฐาน ส่วนคำขอ `/auth/dev/` อื่น (เช่น `/auth/dev/register` ที่สร้างผู้ใช้) ถูกตัดและทำให้เทสไม่ผ่าน
2. คำขอ `/api/...` ที่ไม่ได้ไปที่ `E2E_WEB_API_ORIGIN` ถูกตัด และเทสข้อนั้นไม่ผ่าน ชั้นนี้ครอบถึง proxy `/api` ของ Metro บน `localhost:8081` ที่ส่งต่อไป API บนเครื่อง (`lib/web-api-proxy.ts`)
3. global-setup เปิดหน้าแรกแบบไม่ล็อกอินก่อนเริ่ม ถ้าเห็นคำขอ `/api/...` ไปที่อื่น หยุดทั้งชุดก่อนล็อกอิน **ข้อจำกัด:** หน้าแรกของผู้เยี่ยมชมน่าจะไม่เรียก API (อนุมานจากโค้ด) ถ้าไม่เห็นคำขอเลย ชั้นนี้ตรวจอะไรไม่ได้ และจะพิมพ์บอกไว้ในผลรัน ชั้นที่ 1 และ 2 ยังทำงานในทุกข้อ

ตัวกันตัดคำขออีก 4 แบบ ถ้าเกิดขึ้นเทสข้อนั้นไม่ผ่าน ได้แก่
- ออกจากทุกอุปกรณ์ (Supabase `POST /auth/v1/logout` ที่ไม่ใช่ `scope=local`)
- สมัครสมาชิก (`/auth/v1/signup`)
- ส่งอีเมลรีเซ็ตรหัส (`/auth/v1/recover`)
- คำขอเขียนอื่นไป API ของ `E2E_WEB_API_ORIGIN` (method ที่ไม่ใช่ GET, HEAD หรือ OPTIONS) ที่ไม่อยู่ในรายการที่ยอมให้ผ่าน (`ALLOWED_WRITES` ใน `guard.ts` ตอนนี้มีแค่ `POST /auth/sync`) ชั้นนี้ไม่ครอบคำขอเขียนไป Supabase โดยตรง กันไว้เผื่อหน้าใดเริ่มส่งคำขอเขียนเองตอนเปิด ถ้าเกิด ให้ดูก่อนว่าเป็นคำขออะไร แล้วจึงตัดสินว่าจะเพิ่มในรายการหรือแจ้งทีม ชุดนี้ไม่เรียก `guard.allowWrites` จึงตัดคำขอเขียนทุกตัวเหมือนเดิม (`allowWrites` ใช้ในชุดเทสเขียนข้อมูลบนเว็บเท่านั้น ดูหัวข้อถัดไป)

ข้อ known-bug ใช้ `test.fail` ซึ่งกลับผลของความล้มในข้อนั้น การตรวจคำขอต้องห้ามจึงทำซ้ำตอนปิด worker (fixture `forbiddenLog`) ซึ่งไม่ถูกกลับผล worker คือโปรเซสที่ Playwright ใช้รันเทส ชุดนี้มีตัวเดียว ถ้ามีคำขอต้องห้ามในข้อ known-bug ข้อนั้นยังขึ้นว่า "ล้มตามคาด" แต่จะมี error ขึ้นท้ายรอบ (ในส่วนปิด worker) และรอบนั้นไม่ผ่าน

ตัวกันชั้นที่ 1 และ 2 ทดลองในห้องทดลองแล้ว (4 พ.ย. 2026) ด้วย server จำลอง คำขอที่ถูกตัดไม่ถึง server ส่วน WebSocket ไม่ผ่านตัวกันนี้ (`context.route` ไม่ครอบ) ยังไม่ได้ค้นในโค้ดของแอปว่ามีการเปิด WebSocket ไป API หรือไม่ (ค้นได้ด้วย `grep -rnE "WebSocket|realtime|channel\(" apps/consumer-app packages --include=*.ts --include=*.tsx` การใช้ realtime ของ Supabase มักเรียกผ่าน `.channel(`)

แม้มีตัวกันแล้ว กฎในบันทึก QA 4 พ.ย. 2026 ยังใช้ (โหมด `E2E_WEB_LOCAL_API=yes` ทำตามกฎนี้ด้วยการข้าม `safety-roles.spec.ts` ทั้งไฟล์ ดู "ใช้ API บนเครื่อง"): วันที่ให้เว็บเรียก API บนเครื่อง ห้ามเปิดหน้า `/agent/...` ด้วยบัญชีที่ไม่ใช่นายหน้า และห้ามล็อกอินบนเว็บถ้าไม่ได้ตั้ง `EXPO_PUBLIC_ALLOW_DEV_ROLE_GRANT=false` (ที่ `648dd28` ค่านี้ปิดได้ทั้ง 2 จุด และการไม่ตั้งเลยก็ปิดเหมือนกัน แต่กฎยังให้ตั้ง `false` ไว้ชัด ๆ)

ข้อมูลที่ชุดนี้ยังเขียนลง staging (หรือฐานข้อมูลของทีมผ่าน API บนเครื่องเมื่อตั้ง `E2E_WEB_LOCAL_API=yes` โหมดนี้ตรวจก่อนว่าบัญชีมีอยู่แล้วด้วย `assertLocalQaAccountsLinked`):
- การล็อกอินทุกครั้งเรียก `POST /auth/sync` (`AuthContext.tsx:74-78`) และการเปิดหน้านายหน้าด้วยบัญชี tenant อาจเรียกซ้ำอีกครั้ง (`agent-session.ts:13, 44-51` ใช้คำตอบเดิมซ้ำได้ 30 วินาที) บัญชี qa-* มีอยู่แล้ว จึงเป็นการซิงก์บัญชีเดิม เหมือนตอนเทสด้วยมือ
- ทุกการล็อกอินสร้าง session ใหม่ใน Supabase ให้บัญชีที่ใช้ร่วมกัน ข้อที่ออกจากระบบใช้แบบ scope local จึงไม่ตัด session ของคนอื่น

  - ได้ 401: API มีเส้นทาง refresh แล้ว (รุ่นตั้งแต่ `d2d4554`) ซึ่ง GET บิลอ่านอย่างเดียว คำขอถูก AuthGuard ปฏิเสธก่อนถึงโค้ดของเส้นทาง (`bill-refresh.controller.ts:14-15`) จึงไม่เขียนอะไร ตัวกันจึงปล่อย `GET /bills/mine`, `/bills/mine/next`, `/bills/received`, `/bills/agent/tenants/<เลข>` ผ่าน

### เทสบนเว็บ portal agent

`npm run test:web-ui:portal-agent` รันชุด `tests/web-ui-portal-agent` กับเว็บที่ build แบบ agent.nestyk.com (เพิ่ม 9 พ.ย. 2026 ตามข้อ B4 ของ `docs/qa-fixes/2026-11-09-qa-handoff-review-0a21689.md`) อ่านอย่างเดียว

1. เว็บ: ใน `~/NESTYK/.env` เพิ่ม `EXPO_PUBLIC_WEB_PORTAL=agent` (ค่าอื่นตาม "ใช้ API บนเครื่อง" และต้องไม่ตั้ง `EXPO_PUBLIC_HCAPTCHA_SITE_KEY`) แล้ว `cd apps/consumer-app && npm run build:web && npm run serve:web` (พอร์ต 8090 ตาม `scripts/serve-web-dist.cjs`) รันเสร็จแล้วเอาบรรทัด `EXPO_PUBLIC_WEB_PORTAL` ออก ชุด web-ui อื่นคาด portal `all`
2. Terminal: ตั้งตัวแปรของ "ใช้ API บนเครื่อง" ตามเดิม เพิ่ม `export E2E_WEB_PORTAL=agent E2E_CONSUMER_WEB_URL=http://localhost:8090` และรหัสผ่านกับ uuid ของ qa-agent และ qa-tenant
3. ไม่ตั้ง `E2E_WEB_PORTAL=agent` = ทุกข้อในชุดนี้ข้าม
4. global-setup ของทุกชุด UI เว็บตรวจ portal ของเว็บก่อนล็อกอิน (ยังไม่ล็อกอินเปิด `/tenant`: portal agent ไป `/login?next=/agent` ส่วน portal all ไป `/login?next=/tenant`) ถ้าไม่ตรงกับ `E2E_WEB_PORTAL` หยุดทั้งชุด กันการรันชุดอื่นกับเว็บ portal agent ด้วย ถ้าตรวจไม่ได้ (ไม่ถึง `/login` หรือ next ไม่รู้จัก) ชุด portal agent หยุด ส่วนชุดอื่นพิมพ์เตือนแล้วไปต่อ (รอนานสุดประมาณ 1 นาที)
5. Metro (`npm run web`) อ่าน `.env` ตอนเริ่ม ถ้าเปิด Metro ตอนยังมี `EXPO_PUBLIC_WEB_PORTAL=agent` เว็บ 8081 จะเป็น portal agent จนกว่าจะเอาบรรทัดออกแล้วเปิดใหม่ (ข้อ 4 จะหยุดชุดอื่นให้)

### รหัสผ่านกับรายงาน

ลองในห้องทดลองที่ Playwright 1.63.0 (4 พ.ย. 2026) แล้วพบว่ารหัสผ่านเข้าไปอยู่ในรายงานได้ 2 ทาง ชุดนี้กันไว้ดังนี้

1. ชื่อขั้นในรายงาน HTML: `fill` บันทึกค่าที่พิมพ์ไว้ในชื่อขั้น (เช่น `Fill "<ค่า>"`) ตัวช่วยล็อกอินจึงใส่รหัสผ่านด้วย `evaluate` (`src/web-ui/support/inputs.ts`) ซึ่งบันทึกแค่คำว่า Evaluate
2. ไฟล์ `error-context.md` ของข้อที่ไม่ผ่าน (อยู่ใน `test-results-web-ui/` และถูกคัดลอกไปที่ `playwright-report-web-ui/data/`) เก็บโครงหน้าจอเป็นข้อความ รวมค่าในช่องรหัสผ่านด้วย

### ตรวจก่อนเขียน

ทุกข้อที่แตะลีดหรือนัดถาวรเริ่มด้วย `findQaData` (`src/web-ui/write/web-write-env.ts`) ข้อที่ไม่เรียกคือฟอร์มลีดใหม่ (LW1, LW2, LW6) ไฟล์ห้อง (RW1-RW4) และข้อปุ่ม Edit กับข้อวันเข้าอยู่ของ `lead-room-limits.write.spec.ts` ซึ่งไม่แตะลีดหรือห้องถาวร (ข้อสร้างห้องตรวจผู้ติดต่อของเว็บเองก่อนเขียน ดู "ข้อมูลที่เหลือหลังรัน") (LW2 ส่งคำขอสร้างที่ API ปฏิเสธก่อนเขียน)

`findQaData` หาลีด `E2E-QA-LEAD-1` และห้อง `E2E-QA-ROOM-1` ของ qa-agent บน staging ด้วยชื่อตรงทุกตัวอักษร
- ไม่เจอหรือเจอมากกว่า 1: หยุดก่อนเขียนอะไร ข้อมูลถาวร 2 ตัวนี้สร้างโดย `tests/write` ซึ่งเรียก API บนเครื่อง ถ้า staging ไม่เจอ แปลว่า staging กับฐานข้อมูลของ `tests/write` น่าจะเป็นคนละฐาน ต้องถามทีมก่อนสร้างข้อมูลถาวรบน staging
- ลีดมีเบอร์ไม่ใช่ `0000000000`, เป็น booked หรือมีนัดที่ยังไม่ถึงเวลาซึ่ง note ไม่ขึ้นต้น `E2E-`: หยุด
- ลีดค้างเป็น lost (รอบก่อนล้มกลางทาง): ย้ายกลับเป็น inprogress และยกเลิกนัด `E2E-` ที่ค้างก่อนเริ่ม

### ตัวกันคำขอเขียน

ตัวกันของชุด UI เว็บยังทำงานครบ ต่างแค่แต่ละข้อเรียก `guard.allowWrites({ method, path })` ก่อนกดบันทึก เพื่อปล่อยคำขอเขียนที่ตั้งใจผ่าน (method ตรง และ path ตรง regex ที่ระบุ id ของข้อมูลเทส) คำขอเขียนอื่นยังถูกตัดและทำให้ข้อนั้นไม่ผ่าน ข้อที่เปิด allowWrites ตรวจว่าคำขอที่ปล่อยผ่าน (`guard.allowedWrites`) มีแค่ที่คาด

คำขอที่ห้ามผ่านเสมอแม้อยู่ในรายการ: อัปโหลดรูปห้อง (`/agent/rooms/media/...`) และเขียนโปรโมตด้วย AI (`/agent/rooms/generate-listing-promo`) เพราะค้างใน Storage หรือมีค่าใช้จ่าย

ไฟล์ห้อง (`agent-rooms.write.spec.ts`) ตัดคำขอที่ไปถึง Google ในเบราว์เซอร์ทุกข้อ และนับจำนวนครั้งไว้: ค้นสถานที่ `/agent/places/*` (staging เรียก Google ต่อ) และแผนที่ `maps.googleapis.com` กับ `maps.gstatic.com` ข้อสร้างห้องต้องไม่มีคำขอค้นสถานที่ (กด "Enter location manually" ก่อนพิมพ์ชื่อโครงการ) ส่วนหน้าแก้ตรวจแยกใน RW4 (บั๊กที่รู้แล้ว: หน้าแก้ค้นเองตอนเปิด) นอกจากนี้ข้อสร้างและแก้ห้องตรวจเนื้อคำขอในเบราว์เซอร์ก่อนส่ง ถ้ามีผู้ติดต่อที่ไม่ใช่ผู้ติดต่อของเว็บจะตัดคำขอทิ้ง (service ใช้แถวเดิมจากเบอร์แล้วเขียนทับชื่อ)

การเตรียมและเก็บกวาดใช้ `StagingApi` (`src/web-ui/write/staging-api.ts`) ซึ่งอ่าน token ของแท็บที่ล็อกอินแล้วเรียก API ผ่าน `page.request` (ไม่ผ่านตัวกัน) ใช้กับลีดและนัดของเทสเท่านั้น

### เก็บกวาด

- ทำใน `test.afterEach` (`onCleanup` กับ `runCleanups`) ไม่ใช้ `finally` ในตัวเทส เพราะถ้าข้อนั้นหมดเวลา Playwright รัน afterEach ด้วยเวลาแยกก่อนปิดหน้าเว็บ ส่วน `finally` จะทำงานหลังปิดหน้าเว็บ ซึ่งเรียก API ไม่ได้แล้ว
- ไฟล์ค่าตั้งตั้ง `actionTimeout` 20 วินาที คลิกหรือพิมพ์ที่หาชิ้นส่วนไม่เจอจึงล้มเร็ว ไม่รอจนหมดเวลาของทั้งข้อ
- ลีดถาวร: `restoreLead` คืนทุกช่องที่ฟอร์มแก้ได้ให้เท่าค่าก่อนข้อนั้น (ไม่ใช่แค่ notes เพราะถ้าฟอร์มส่งช่องอื่นผิด ค่าที่ผิดจะกลายเป็นค่าตั้งต้นของรอบหน้า) และจบที่ inprogress
- ข้อ `[footprint]` ท้ายไฟล์ลีดอ่านลีดตรง ๆ (ก่อน `findQaData` ซึ่งซ่อมลีดที่ค้างเป็น lost) แล้วตรวจว่าเป็น inprogress และ notes กับเหตุผล lost ไม่มีรหัสรอบนี้
- ทุกไฟล์ที่เรียก `onCleanup` ต้องมี `test.afterEach(runCleanups)` ถ้าลืม ข้อถัดไปที่เรียก `onCleanup` จะหยุดพร้อมบอกสาเหตุ

### ข้อมูลที่เหลือหลังรัน

- ลีดถาวร: จบที่ inprogress และช่องที่ฟอร์มแก้ได้เท่าค่าก่อนรัน
- จำนวนลีดและห้องที่มีป้าย `E2E-` ระหว่างไฟล์ลีด (`agent-leads.write.spec.ts` รันก่อนไฟล์อื่นทุกไฟล์ จึงไม่นับการเปลี่ยนของไฟล์ห้อง ไฟล์สร้างลีด และ `lead-room-limits.write.spec.ts`): ต้องเท่าเดิม ข้อ `[footprint]` แรกของไฟล์ลีดนับและเก็บค่าไว้ในไฟล์ใต้ `test-results-web-ui-write/` (worker ที่เริ่มใหม่หลังข้อแดงยังอ่านได้) ข้อสุดท้ายเทียบ ถ้าไม่ได้รันข้อแรก (เช่น รันด้วย `--grep`) ข้อสุดท้ายข้าม

## ยังไม่ครอบคลุม

- เทสที่สร้างหรือแก้ข้อมูล: `tests/write` มีเทสนำร่องของลีด (แก้ notes และเปลี่ยนสถานะลีดถาวร) และเทสวงจรเช่าห้องที่เดินเส้นทางปกติ 1 เส้นทาง (สร้างห้อง นัด ข้อเสนอ ผู้เช่า สัญญา 3 ฉบับ สลิปและใบเสร็จ ส่งมอบ บิล 1 ใบ แจ้งย้ายออก คืนมัดจำ) ยังไม่ได้เทสกรณีที่ต้องถูกปฏิเสธของเส้นทางเหล่านี้ ค่าอื่นของแต่ละฟอร์ม การตีกลับสลิป ค่าปรับจ่ายช้า ไม่ต่อสัญญา ต่อสัญญา ลิงก์แชร์ และจับคู่ห้อง
