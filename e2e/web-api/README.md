# ชุดเทส E2E ของ NESTYK: API และเว็บ (Playwright)

ชุดเทสนี้เรียกระบบที่รันอยู่จริงจากภายนอก เหมือนที่แอปมือถือและเว็บเรียก ตอนนี้มีเทส API ของ `apps/api` ซึ่งไม่สร้างและไม่แก้ข้อมูล (ดูข้อตกลงด้านล่าง) เทสหน้าเว็บจะเพิ่มในขั้นถัดไป

โฟลเดอร์นี้มี `package.json` ของตัวเอง และไม่อยู่ใน workspaces ของ monorepo การติดตั้งที่นี่จึงไม่แตะ `package-lock.json` ของราก

## สิ่งที่ต้องมีก่อนรัน

- Node.js 22 ขึ้นไป
- API ที่พอร์ต 4000 ต่อกับฐานข้อมูลที่มีตารางและข้อมูลของทีม (ฐานข้อมูลในเครื่องผ่าน Supabase หรือฐานข้อมูลของทีมบนคลาวด์ ตามค่า `DATABASE_URL` ใน `.env.api`)
- ไฟล์ `.env.api` ตั้ง `ALLOW_DEV_AUTH=true` (เทสล็อกอินด้วยบัญชี QA ของทีมแบบนักพัฒนา ไม่ใช้รหัสผ่าน)
- ไฟล์ `.env.api` ตั้ง `ALLOW_DEV_ROLE_GRANT=true` สำหรับเทส `POST /auth/dev/roles` ใน `auth.spec.ts` (ส่งเฉพาะชื่อบทบาทที่ต้องถูกปฏิเสธ) ถ้าไม่ตั้ง API ตอบ 403 และข้อนั้นไม่ผ่าน
  - ถ้า API ปิดสวิตช์นี้ไว้ด้วยเหตุผลอื่น ไม่ต้องเปิดเพื่อให้เทสข้อนี้ผ่าน เพราะสวิตช์นี้ให้ผู้ใช้ทุกคนที่ล็อกอินได้ (ทั้ง dev token และ token ของ Supabase) ขอหรือถอนบทบาทของบัญชีตัวเองได้ รวมบทบาท admin (`POST` และ `DELETE /auth/dev/roles` ใน `apps/api/src/auth/auth.service.ts:166-216` กับ `apps/api/src/auth/guards/auth.guard.ts:63-100`)
- บัญชี QA แยกบทบาทของทีม `qa-guest`, `qa-tenant`, `qa-landlord`, `qa-agent`, `qa-admin` (`@nestyk.test`) มีในฐานข้อมูลที่ API ใช้ เทสที่ต้องล็อกอินใช้บัญชีเหล่านี้ (เทส 401 ใช้ผู้เรียกที่ไม่ล็อกอินหรือบัตรผ่านที่ใช้ไม่ได้)
  - `qa-agent` เป็นผู้เรียกหลัก (fixture `agent` ของเทสกลุ่ม `agent/*` เกือบทั้งหมด) **ต้องตั้ง uuid ทุกครั้ง** ถ้าไม่ตั้ง global-setup หยุดทั้งชุด
    บัญชีนี้ต้องมีลีดที่สถานะไม่ใช่ lost และยังไม่เป็นผู้เช่าอย่างน้อย 1 ราย และห้องอย่างน้อย 2 ห้อง
    ถ้าขาดลีดหรือห้อง เทสข้อนั้นไม่ผ่านพร้อมข้อความว่า qa-agent ต้องมีอะไร ถ้าขาดข้อมูลบางแบบ (ห้องที่มีราคา ชื่อประกาศ เลขห้อง ลีดที่ระบุจังหวัดหรือทำเล ลีดที่ถูกแก้หลังสร้าง บิลที่รอนายหน้าตรวจ) เทสข้อนั้นข้ามพร้อมเหตุผล ผลรวมจึงเขียวได้ทั้งที่บางข้อไม่ได้ตรวจ ให้ดูรายการข้อที่ข้ามทุกครั้ง ถ้าข้อมูลไม่พอให้แจ้งทีม ห้ามสร้างข้อมูลเองในฐานข้อมูลของทีม
    นับเมื่อ 21 ต.ค. 2026 ในฐานข้อมูลของทีม: `total` ของ `GET /agent/leads` ได้ 20 และของ `GET /agent/listings` ได้ 33 (ยังไม่ได้นับว่ามีลีดที่สถานะไม่ใช่ lost และยังไม่เป็นผู้เช่ากี่ราย)
  - `qa-tenant` ใช้กับ `bills/mine/*` และ `contracts/mine*` ส่วน `qa-landlord` ใช้กับ `bills/received/*` กับ `POST /auth/dev/roles` และเป็นบัญชีที่ถูกค้นในการค้นบัญชีเจ้าของห้อง ทุกบัญชีใช้กับเทสสิทธิ์ใน `roles.spec.ts`

  - ทุกฐานข้อมูล (`supabase/MIGRATION-RULES.md` หัวข้อภาพรวมและข้อห้ามข้อ 3): รัน `db:check` แบบมี `-- --check` ทุกครั้ง ห้ามตอบ `y` ถ้าสคริปต์ถามว่าจะปรับฐานข้อมูลไหม และห้ามรันไฟล์ใน `apps/api/migrations/` ซึ่งเป็นโฟลเดอร์ของระบบเก่า (ผลของ `db:check` พิมพ์เป็น `migrations/<ชื่อไฟล์>`) ถ้า `db:check` หรือบรรทัด `[SchemaDrift]` ใน log ของ API บอกให้รัน `db:check` แบบไม่มี `--check` ห้ามทำตาม ทีมแก้ด้วยการเพิ่มไฟล์ใน `supabase/migrations/`
  - **ถ้า `DATABASE_URL` ชี้ไปที่ฐานข้อมูลของทีม ห้ามรันสคริปต์ `db:*` ทุกตัว (`db:push` ทุกแบบ, `db:seed`, `db:test-users`, `db:contract-deposits`, `db:contract-closure` ตามรายการใน `apps/api/package.json`) ยกเว้น `db:check -- --check` และห้ามรัน SQL ที่แก้ฐานข้อมูลเอง (รวม SQL ที่ `db:check` พิมพ์ให้ตรวจแล้วรันเอง)** ให้แจ้งทีมให้ขึ้น migration แทน (`db:push -- --check` ก็สั่งรันจริงแล้วค่อยย้อนกลับ ระหว่างนั้นถือ lock ตารางของทีม ดู `supabase/MIGRATION-RULES.md`)

ก่อนเริ่มเทส `src/global-setup.ts` ตรวจ 5 อย่างตามลำดับ ถ้าไม่ผ่านจะหยุดทั้งชุดและบอกสาเหตุ: API ตอบที่ `/health`, ตั้ง uuid ของ `qa-agent` แล้ว, บัญชี QA ทุกบัญชีที่ตั้ง uuid ไว้ (รูปแบบ uuid ถูก ไม่ซ้ำกัน API รับบัตรผ่านแบบนักพัฒนา มีในตาราง `users` อีเมลตรงกับบทบาท และบทบาทตรงกับ migration ทุกตัว แล้วพิมพ์บรรทัด `[บัญชี QA] ตรวจแล้ว N จาก 5 บัญชี` บอกว่าบัญชีไหนไม่ได้ตั้ง), `GET /agent/leads` ของ qa-agent ได้ 200 (ไม่ใช่ 5xx) และ API มีตัวตรวจ id ของรุ่น `f7d52ed` (id ที่เกินช่วงได้ 400 พร้อมข้อความที่ชุดเทสคาด) global-setup ไม่ได้นับลีดและห้องของ qa-agent ส่วนข้ออื่นข้างบนชุดเทสไม่ได้ตรวจ ต้องตรวจเองก่อนรัน เช่น `npm run db:check -w @nestyk/api -- --check` ต้องได้ ✓ และ 2 คำสั่งนี้ต้องไม่มีผลลัพธ์ ซึ่งแปลว่าโค้ดนอก `e2e/` บนเครื่อง รวมไฟล์ที่แก้ค้างและไฟล์ใหม่ที่ยังไม่ commit เหมือน develop (รันจากโฟลเดอร์ไหนใน repo ก็ได้ `origin/develop` คือ develop ตอน fetch ครั้งล่าสุด จึงควร fetch ก่อน)

## ข้อตกลงของชุดเทส

- ชื่อเทสเป็นภาษาอังกฤษ คอมเมนต์เป็นภาษาไทย
- ไฟล์เทสไม่ส่งคำขอ HTTP เอง ให้เรียกผ่านตัวเรียกใน `src/api/` (หลักเดียวกับ Page Object: ถ้าเส้นทางของ API เปลี่ยน แก้ที่เดียว)
- ตัวเรียกใน `src/api/` คืนคำตอบดิบและไม่ตรวจผล การตรวจอยู่ในไฟล์เทส เทสจึงตรวจได้ทั้งกรณีสำเร็จและกรณีที่ API ต้องปฏิเสธ
- เทสไม่ผูกกับจำนวนข้อมูลที่แน่นอน (เช่น ไม่ตรวจว่ามี 30 ห้อง) แต่ต้องมีลีดและห้องของ qa-agent อย่างน้อยตามที่บอกในหัวข้อ "สิ่งที่ต้องมีก่อนรัน"
- เทสที่มีอยู่ตอนนี้ไม่สร้างและไม่แก้ข้อมูล จึงรันพร้อมกันได้ เมื่อเพิ่มเทสที่สร้างหรือแก้ข้อมูล ต้องมีวิธีเก็บกวาดข้อมูลของเทสเองด้วย
- เทสของเส้นทางที่บันทึกข้อมูล (POST, PUT, PATCH และ DELETE ของผู้เช่า สัญญา และบิล) ส่งเฉพาะคำขอที่ระบบต้องปฏิเสธ และใช้ id ที่ไม่มีอยู่จริง (2147483647) ถ้าคำขอผ่านการตรวจค่าไปได้ ระบบจะหาข้อมูลไม่เจอแล้วตอบ 404 ก่อนบันทึก ยกเว้น `POST bills/received/:id/late-fee` ที่ตอบ 403 ก่อนบันทึก (ตรวจลำดับนี้ในโค้ดของ API ที่ qa/e2e `4833ace` (develop `b228ee3`) แล้วทุกเส้นทางของผู้เช่าและสัญญาที่เทส ส่วนกลุ่ม `bills/*` และเส้นทางที่เพิ่มใน develop `9644dd9` ตรวจที่ `9644dd9`)
  - `POST /agent/contracts/:id/witness-sign` ตรวจชื่อพยานและลายเซ็นก่อนหาสัญญา เทส 404 จึงส่งภาพลายเซ็น PNG ที่อ่านได้ไปด้วย
  - เส้นทางลงนามผ่านลิงก์แบบไม่ต้องล็อกอิน (`/public/contract-sign/:token`) ทีมลบแล้วใน develop `b228ee3` เทสตรวจว่าเปิดไม่ได้แล้ว (NestJS ตอบว่าไม่มีเส้นทางนี้)
- `POST /auth/dev/roles` บันทึกบทบาทให้บัญชีทันทีถ้าชื่อบทบาทอยู่ในรายการที่ขอได้และมีแถวใน `master_roles` เทสส่งแค่ชื่อที่ไม่มีอยู่จริงกับชื่อ owner ที่เลิกใช้แล้ว ซึ่ง `grantDevRole` ปฏิเสธก่อนอ่านตารางบทบาท (`apps/api/src/auth/auth.service.ts:166-172` ที่ develop `84087e2`)
  - ก่อนส่งชื่อ owner เทสตรวจว่าบัญชีมี landlord ไม่มี owner และดูรายการบทบาทที่ขอได้จากคำตอบของชื่อที่ไม่มีอยู่จริง ถ้ารายการยังมี owner (API รุ่นก่อน 84087e2) เทสจะหยุดก่อนส่ง
- เส้นทางค้นบัญชีเจ้าของห้อง (`GET /agent/contracts/owner-users`) ตอบข้อมูลส่วนตัว เทสตรวจแค่จำนวนกับ id และไม่เทียบทั้งรายการ เพราะถ้าเทสไม่ผ่าน Playwright จะพิมพ์ค่าที่เทียบออกมาในผลรัน
- บั๊กที่รู้แล้วและรอแก้: เขียนเทสตามพฤติกรรมที่ถูกต้อง แล้วใส่ `test.fail()` กับป้าย `@known-bug` ผลรวมจะยังผ่าน และเมื่อบั๊กถูกแก้ เทสข้อนั้นจะแดงเพื่อเตือนให้ลบ `test.fail()` ออก ดูรายการได้ด้วย `npx playwright test --grep @known-bug --list` (บั๊ก 500 ของ id เกินช่วงและ query ซ้ำ 9 ข้อถูกแก้แล้วที่ DEV/main `f7d52ed` ชุดเทสจึงต้องรันกับ API รุ่น `f7d52ed` ขึ้นไป ดูหัวข้อ "สิ่งที่ต้องมีก่อนรัน" ตอนนี้มี 3 ข้อ: dev token ที่ส่วน uuid ไม่ใช่ uuid ได้ 500 แทน 401 ใน `auth.spec.ts` พบที่ develop `a09e6d2` และ `POST /agent/contracts/:id/early-end` กับ `POST /agent/contracts/:id/not-renewing` ได้ 500 แทน 404 ใน `agent-contracts.spec.ts` พบที่ develop `9644dd9` (สาเหตุยังเป็นการอนุมานจากโค้ดและผลห้องทดลอง ดูคอมเมนต์ในไฟล์เทส) ทุกข้อมีเทสคู่ที่ตรวจขั้นต่ำว่าคำขอถูกปฏิเสธ)

## ตัวแปรแวดล้อม

ตัวที่ต้องตั้งทุกครั้งคือ `E2E_QA_AGENT_UUID` ตัวอื่นไม่ต้องตั้งถ้าเทสกับระบบในเครื่องตามค่าเริ่มต้น

| ชื่อ | ค่าเริ่มต้น | ใช้ทำอะไร |
| --- | --- | --- |
| `E2E_API_BASE_URL` | `http://localhost:4000/api/v1` | ที่อยู่ของ API |
| `E2E_WEB_BASE_URL` | `http://localhost:3000` | ที่อยู่ของเว็บ (ยังไม่ถูกใช้) |
| `E2E_QA_AGENT_UUID` | ไม่มี ต้องตั้ง (ไม่ตั้ง = global-setup หยุดทั้งชุด) | uuid ของ `qa-agent@nestyk.test` ผู้เรียกหลักของชุดเทส จาก Supabase > Authentication > Users |
| `E2E_QA_GUEST_UUID`, `E2E_QA_TENANT_UUID`, `E2E_QA_LANDLORD_UUID`, `E2E_QA_ADMIN_UUID` | ไม่ตั้ง (เทสที่ใช้บัญชีนั้นข้าม) | uuid ของบัญชี `qa-<บทบาท>@nestyk.test` จาก Supabase > Authentication > Users |
| `E2E_QA_EMAIL_DOMAIN` | `nestyk.test` | โดเมนอีเมลของบัญชี QA (ต้องตรงกับ `TEST_USER_EMAIL_DOMAIN` ที่ทีมใช้) migration ผูกเฉพาะ `@nestyk.test` ถ้าทีมใช้โดเมนอื่น ทีมต้องผูกบัญชีเองด้วย `apps/api/scripts/db-test-users.cjs` |

ตั้ง uuid ของบัญชี QA ใน Terminal ก่อนรัน: **ใส่คำสั่งข้างล่างทีละบรรทัด** (อย่าวางทั้งก้อน เพราะ bash รุ่นเก่าจะเอาบรรทัดถัดไปเป็นคำตอบของ `read`) แล้ววาง UID เมื่อถูกถาม (ตัวอักษรไม่ขึ้นบนจอ)
อย่าพิมพ์ UID ไว้ในคำสั่ง `export` ตรง ๆ เพราะ Terminal (zsh ของ macOS) เก็บคำสั่งที่พิมพ์ลงไฟล์ประวัติ (`~/.zsh_history`) ส่วน `read` ไม่ถูกเก็บ
ค่าอยู่แค่ใน Terminal หน้าต่างนั้น ปิดหน้าต่างแล้วต้องตั้งใหม่ ก่อนอ่านผล ให้ดูบรรทัด `[บัญชี QA] ตรวจแล้ว N จาก 5 บัญชี` ว่า N ตรงกับจำนวนที่ตั้ง (ถ้าตั้งแค่ qa-agent เทสสิทธิ์ส่วนใหญ่และเทสของ qa-tenant กับ qa-landlord จะข้าม แม้ผลรวมจะเขียว)

```bash
printf 'UID ของ qa-guest: ';    read -rs E2E_QA_GUEST_UUID;    echo
printf 'UID ของ qa-tenant: ';   read -rs E2E_QA_TENANT_UUID;   echo
printf 'UID ของ qa-landlord: '; read -rs E2E_QA_LANDLORD_UUID; echo
printf 'UID ของ qa-agent: ';    read -rs E2E_QA_AGENT_UUID;    echo
printf 'UID ของ qa-admin: ';    read -rs E2E_QA_ADMIN_UUID;    echo
export E2E_QA_GUEST_UUID E2E_QA_TENANT_UUID E2E_QA_LANDLORD_UUID E2E_QA_AGENT_UUID E2E_QA_ADMIN_UUID
npm test
```

บัญชีที่ยังไม่มี UID ให้กด Enter ข้ามไป (ค่าว่าง = ไม่ได้ตั้ง เทสของบัญชีนั้นจะข้าม) ยกเว้น qa-agent ซึ่งต้องมีทุกครั้ง

ถ้าทีมเปลี่ยนรายการบทบาทของ `agent/leads/*` หรือ `contracts/mine*` (2 กลุ่มที่ global-setup ใช้ยืนยันว่าบัญชี QA มีอยู่) ชุดเทสจะหยุดทั้งชุดที่ global-setup พร้อมข้อความบอกเส้นทาง แทนที่จะเห็นเป็นเทสที่ล้มรายข้อ ตั้งใจให้หยุดก่อนเรียก `POST /auth/sync`

## ยังไม่ครอบคลุม

- เทสที่สร้างหรือแก้ข้อมูล เช่น สร้างลีด สร้างห้อง ทำสัญญา
- การกันสิทธิ์ตามบทบาท: `roles.spec.ts` (ใช้บัญชี QA) ตรวจ 403 ของเส้นทาง GET ตัวแทนของทุก controller ยกเว้นกลุ่มห้อง (`agent/rooms/*`) ลิงก์แชร์ห้อง (`agent/listings/:id/share-links`) การนัดดูห้อง และการจับคู่ห้องให้ลีด (ยังไม่มีตัวเรียกใน `src/api/`) การเลือกเส้นทางตัวแทนพึ่งการที่ทุก controller ตั้ง `@Roles` ระดับ class `party-contracts.controller.ts` มี `@Roles('landlord')` ระดับ method: `GET mine/deal-offers` กับ `POST mine/deal-offers/:id/confirm` (ตั้งแต่ develop `f845ac6`) และ `GET mine/reminders` (ตั้งแต่ develop `8a62e39`) และ RolesGuard ใช้ค่าระดับ method แทนระดับ class (`getAllAndOverride`) ทั้ง 3 เส้นทางนี้จึงตรวจแยกในกลุ่ม "landlord contract routes" ถ้าทีมเพิ่ม `@Roles` ระดับ method ให้เส้นทางอื่นอีก เทสจะจับไม่ได้ และไม่ตรวจ 403 ของเส้นทาง POST/PUT/PATCH/DELETE (ถ้าบทบาทถูกคำขอจะบันทึกจริง) ยกเว้น `POST mine/deal-offers/:id/confirm` ซึ่งส่งเนื้อคำขอว่างที่ service ปฏิเสธด้วย 400 ก่อนแตะฐานข้อมูล ถ้าไม่ได้ตั้ง uuid ของบัญชี QA บัญชีไหน เทสที่ใช้บัญชีนั้นข้าม
