# ชุดเทส E2E ของ NESTYK: API และเว็บ (Playwright)

ชุดเทสนี้เรียกระบบที่รันอยู่จริงจากภายนอก เหมือนที่แอปมือถือและเว็บเรียก ตอนนี้มีเทส API ของ `apps/api` ซึ่งไม่สร้างและไม่แก้ข้อมูล (ดูข้อตกลงด้านล่าง) เทสหน้าเว็บจะเพิ่มในขั้นถัดไป

โฟลเดอร์นี้มี `package.json` ของตัวเอง และไม่อยู่ใน workspaces ของ monorepo การติดตั้งที่นี่จึงไม่แตะ `package-lock.json` ของราก

## สิ่งที่ต้องมีก่อนรัน

- Node.js 22 ขึ้นไป
- API ที่พอร์ต 4000 ต่อกับฐานข้อมูลที่มีตารางและข้อมูลตัวอย่างของทีม (ฐานข้อมูลในเครื่องผ่าน Supabase หรือฐานข้อมูลของทีมบนคลาวด์ ตามค่า `DATABASE_URL` ใน `.env.api`)
- ไฟล์ `.env.api` ตั้ง `ALLOW_DEV_AUTH=true` (เทสล็อกอินด้วยบัญชีตัวอย่างของทีม ไม่ใช้รหัสผ่าน)
- ไฟล์ `.env.api` ตั้ง `ALLOW_DEV_ROLE_GRANT=true` สำหรับเทส `POST /auth/dev/roles` ใน `auth.spec.ts` (ส่งเฉพาะชื่อบทบาทที่ต้องถูกปฏิเสธ) ถ้าไม่ตั้ง API ตอบ 403 และข้อนั้นไม่ผ่าน
  - ถ้า API ปิดสวิตช์นี้ไว้ด้วยเหตุผลอื่น ไม่ต้องเปิดเพื่อให้เทสข้อนี้ผ่าน เพราะสวิตช์นี้ให้ผู้ใช้ทุกคนที่ล็อกอินได้ (ทั้ง dev token และ token ของ Supabase) ขอหรือถอนบทบาทของบัญชีตัวเองได้ รวมบทบาท admin (`POST` และ `DELETE /auth/dev/roles` ใน `apps/api/src/auth/auth.service.ts:166-216` กับ `apps/api/src/auth/guards/auth.guard.ts:63-100`)
- รัน API จากโค้ดของ develop (ถ้ารันจาก qa/e2e โค้ดนอก `e2e/` ต้องเหมือน develop): งานเทสใช้ develop เป็นฐานหลักตั้งแต่ 16 ต.ค. 2026 ของใหม่จาก DEV/main ยังไม่นับจนกว่าทีมจะแจ้งว่านำเข้า develop แล้ว
- API รุ่น `f7d52ed` ขึ้นไป ซึ่ง develop มีแล้ว (ชุดเทสเขียนตามพฤติกรรมของรุ่นนี้ เช่น id ที่เกินช่วงต้องได้ 400)
- API กับฐานข้อมูลใช้ชื่อบทบาทของ develop `84087e2` ขึ้นไป: บทบาท owner เปลี่ยนชื่อเป็น landlord (`supabase/migrations/20261016100000_rename_owner_role_to_landlord.sql`) เทสที่ตรวจบทบาท landlord ไม่ผ่านกับ API หรือฐานข้อมูลรุ่นก่อน
  - ตอนเปิด API ตรวจตาราง `master_roles` เอง (`apps/api/src/database/role-catalog.check.ts`) ถ้ายังขาด landlord หรือยังมี owner อยู่ API จะไม่เปิด และข้อความจะบอกให้รัน `db:push` หรือ migration นั้น ถ้า `DATABASE_URL` ชี้ไปที่ฐานข้อมูลของทีม ห้ามทำตาม ให้แจ้งทีม (ดูข้อห้ามด้านล่าง)
- ฐานข้อมูลที่ API ใช้มีโครงสร้างตรงกับโค้ดของ API: `npm run db:check -w @nestyk/api -- --check` ต้องได้ ✓ (ตัวเลือก `--check` = รายงานอย่างเดียว ไม่ถาม ไม่แก้)
  - migration ของทีมอยู่ที่ `supabase/migrations/` และขึ้นด้วย `npm run db:push -w @nestyk/api` (ดู `supabase/MIGRATION-RULES.md`)
  - ทุกฐานข้อมูล (`supabase/MIGRATION-RULES.md` หัวข้อภาพรวมและข้อห้ามข้อ 3): รัน `db:check` แบบมี `-- --check` ทุกครั้ง ห้ามตอบ `y` ถ้าสคริปต์ถามว่าจะปรับฐานข้อมูลไหม และห้ามรันไฟล์ใน `apps/api/migrations/` ซึ่งเป็นโฟลเดอร์ของระบบเก่า (ผลของ `db:check` พิมพ์เป็น `migrations/<ชื่อไฟล์>`) ถ้า `db:check` หรือบรรทัด `[SchemaDrift]` ใน log ของ API บอกให้รัน `db:check` แบบไม่มี `--check` ห้ามทำตาม ทีมแก้ด้วยการเพิ่มไฟล์ใน `supabase/migrations/`
  - **ถ้า `DATABASE_URL` ชี้ไปที่ฐานข้อมูลของทีม ห้ามรัน `db:push` ทุกแบบ และห้ามรัน SQL ที่แก้ฐานข้อมูลเอง (รวม SQL ที่ `db:check` พิมพ์ให้ตรวจแล้วรันเอง)** ให้แจ้งทีมให้ขึ้น migration แทน (`db:push -- --check` ก็สั่งรันจริงแล้วค่อยย้อนกลับ ระหว่างนั้นถือ lock ตารางของทีม ดู `supabase/MIGRATION-RULES.md`)

ก่อนเริ่มเทส `src/global-setup.ts` ตรวจ 4 อย่าง ถ้าไม่ผ่านจะหยุดทั้งชุดและบอกสาเหตุ: API ตอบที่ `/health`, บัญชีตัวอย่างล็อกอินได้และมีบทบาท agent, `GET /agent/leads` ไม่ได้ 5xx และ API มีตัวตรวจ id ของรุ่น `f7d52ed` (id ที่เกินช่วงได้ 400 พร้อมข้อความที่ชุดเทสคาด) ส่วนข้ออื่นข้างบนชุดเทสไม่ได้ตรวจ ต้องตรวจเองก่อนรัน เช่น `npm run db:check -w @nestyk/api -- --check` ต้องได้ ✓ และ 2 คำสั่งนี้ต้องไม่มีผลลัพธ์ ซึ่งแปลว่าโค้ดนอก `e2e/` บนเครื่อง รวมไฟล์ที่แก้ค้างและไฟล์ใหม่ที่ยังไม่ commit เหมือน develop (รันจากโฟลเดอร์ไหนใน repo ก็ได้ `origin/develop` คือ develop ตอน fetch ครั้งล่าสุด จึงควร fetch ก่อน)

```bash
git diff --stat origin/develop -- ':(top)' ':(top,exclude)e2e'
git status --short -- ':(top)' ':(top,exclude)e2e'
```

## ติดตั้ง

```bash
cd e2e/web-api
npm ci
```

เทส API ไม่เปิดเบราว์เซอร์ จึงยังไม่ต้องติดตั้งเบราว์เซอร์ของ Playwright

## รัน

| คำสั่ง | ทำอะไร |
| --- | --- |
| `npm test` | รันทุกเทส |
| `npm run test:api` | รันเฉพาะเทส API |
| `npm run test:smoke` | รันเฉพาะเทสหลักที่ติดป้าย `@smoke` (ใช้ตรวจเร็ว ๆ ว่าระบบยังใช้ได้) |
| `npx playwright test tests/api/auth.spec.ts` | รันไฟล์เดียว |
| `npx playwright test -g "price"` | รันเฉพาะเทสที่ชื่อมีคำที่ระบุ |
| `npm run report` | เปิดรายงาน HTML ของรอบล่าสุด |
| `npm run typecheck` | ตรวจชนิดข้อมูลของโค้ดเทสด้วย TypeScript |

## โครงสร้าง

```
e2e/web-api/
├── playwright.config.ts     ค่าตั้งของ Playwright
├── src/
│   ├── config/env.ts        ที่อยู่ของระบบและบัญชีตัวอย่าง (เปลี่ยนได้ด้วยตัวแปรแวดล้อม)
│   ├── api/                 ตัวเรียก API แยกตามเรื่อง และรูปแบบข้อมูลที่เทสตรวจ
│   ├── fixtures/            ของที่เตรียมให้ทุกเทส: ผู้เรียกที่ไม่ล็อกอิน (anonymous) และนายหน้าที่ล็อกอินแล้ว (agent)
│   ├── support/             ตัวช่วยตรวจผลที่ใช้ร่วมกัน เช่น ตรวจรหัสตอบกลับ และเดินอ่านทุกหน้า
│   └── global-setup.ts      ตรวจว่าระบบพร้อมก่อนเริ่มเทสทั้งชุด
└── tests/
    └── api/                 ไฟล์เทส ไฟล์ละเรื่อง
```

## ข้อตกลงของชุดเทส

- ชื่อเทสเป็นภาษาอังกฤษ คอมเมนต์เป็นภาษาไทย
- ไฟล์เทสไม่ส่งคำขอ HTTP เอง ให้เรียกผ่านตัวเรียกใน `src/api/` (หลักเดียวกับ Page Object: ถ้าเส้นทางของ API เปลี่ยน แก้ที่เดียว)
- ตัวเรียกใน `src/api/` คืนคำตอบดิบและไม่ตรวจผล การตรวจอยู่ในไฟล์เทส เทสจึงตรวจได้ทั้งกรณีสำเร็จและกรณีที่ API ต้องปฏิเสธ
- เทสไม่ผูกกับจำนวนข้อมูลที่แน่นอน (เช่น ไม่ตรวจว่ามี 30 ห้อง) แต่ต้องมีข้อมูลตัวอย่างอย่างน้อย 1 รายการ
- เทสที่มีอยู่ตอนนี้ไม่สร้างและไม่แก้ข้อมูล จึงรันพร้อมกันได้ เมื่อเพิ่มเทสที่สร้างหรือแก้ข้อมูล ต้องมีวิธีเก็บกวาดข้อมูลของเทสเองด้วย
- เทสของเส้นทางที่บันทึกข้อมูล (POST และ PATCH ของผู้เช่าและสัญญา) ส่งเฉพาะคำขอที่ระบบต้องปฏิเสธ และใช้ id ที่ไม่มีอยู่จริง (2147483647) หรือลิงก์ลงนามที่ไม่เคยถูกออก ถ้าคำขอผ่านการตรวจค่าไปได้ ระบบจะหาข้อมูลไม่เจอแล้วตอบ 404 ก่อนบันทึก (ตรวจลำดับนี้ในโค้ดของ API ที่ commit `f9b9bea` แล้วทุกเส้นทางที่เทส ส่วนกลุ่ม `bills/*` ตรวจที่ DEV/main `f7d52ed`)
- `POST /auth/dev/roles` บันทึกบทบาทให้บัญชีทันทีถ้าชื่อบทบาทอยู่ในรายการที่ขอได้และมีแถวใน `master_roles` เทสส่งแค่ชื่อที่ไม่มีอยู่จริงกับชื่อ owner ที่เลิกใช้แล้ว ซึ่ง `grantDevRole` ปฏิเสธก่อนอ่านตารางบทบาท (`apps/api/src/auth/auth.service.ts:166-172` ที่ develop `84087e2`)
  - ก่อนส่งชื่อ owner เทสตรวจว่าบัญชีมี landlord ไม่มี owner และดูรายการบทบาทที่ขอได้จากคำตอบของชื่อที่ไม่มีอยู่จริง ถ้ารายการยังมี owner (API รุ่นก่อน 84087e2) เทสจะหยุดก่อนส่ง
- เส้นทางค้นบัญชีเจ้าของห้อง (`GET /agent/contracts/owner-users`) ตอบข้อมูลส่วนตัว เทสตรวจแค่จำนวนกับ id และไม่เทียบทั้งรายการ เพราะถ้าเทสไม่ผ่าน Playwright จะพิมพ์ค่าที่เทียบออกมาในผลรัน
- บั๊กที่รู้แล้วและรอแก้: เขียนเทสตามพฤติกรรมที่ถูกต้อง แล้วใส่ `test.fail()` กับป้าย `@known-bug` ผลรวมจะยังผ่าน และเมื่อบั๊กถูกแก้ เทสข้อนั้นจะแดงเพื่อเตือนให้ลบ `test.fail()` ออก ดูรายการได้ด้วย `npx playwright test --grep @known-bug --list` (ตั้งแต่ DEV/main `f7d52ed` ไม่มีเทสแบบนี้เหลืออยู่ เพราะบั๊ก 500 ของ id เกินช่วงและ query ซ้ำ 9 ข้อถูกแก้แล้ว ชุดเทสจึงต้องรันกับ API รุ่น `f7d52ed` ขึ้นไป ดูหัวข้อ "สิ่งที่ต้องมีก่อนรัน")

## ตัวแปรแวดล้อม

ไม่ต้องตั้งถ้าเทสกับระบบในเครื่องตามค่าเริ่มต้น

| ชื่อ | ค่าเริ่มต้น | ใช้ทำอะไร |
| --- | --- | --- |
| `E2E_API_BASE_URL` | `http://localhost:4000/api/v1` | ที่อยู่ของ API |
| `E2E_WEB_BASE_URL` | `http://localhost:3000` | ที่อยู่ของเว็บ (ยังไม่ถูกใช้) |
| `E2E_DEV_USER_UUID` | บัญชีตัวอย่างของทีม | ผู้ใช้ที่เทสล็อกอินแบบนักพัฒนา |
| `E2E_DEV_USER_EMAIL` | บัญชีตัวอย่างของทีม | อีเมลของผู้ใช้คนเดียวกัน |

## ยังไม่ครอบคลุม

- เทสที่สร้างหรือแก้ข้อมูล เช่น สร้างลีด สร้างห้อง ทำสัญญา
- การกันสิทธิ์ตามบทบาท (ผู้ใช้ที่ไม่มีบทบาทนายหน้าต้องได้ 403) เช่น `agent/places` ซึ่งตั้งแต่ develop `84087e2` รับเฉพาะ agent (`agent-places.controller.ts:10-11` ก่อนหน้านั้นบรรทัดนี้คือ `@Roles('agent', 'owner')`) ต้องมีบัญชีทดสอบที่มีบทบาท landlord อย่างเดียว ซึ่งชุดเทสยังไม่มี (รอขอทีม)
- กลุ่มผู้เช่าและสัญญา: การสร้างผู้เช่าหรือสัญญาสำเร็จ การออกเอกสาร การลงนาม และการกันข้อมูลข้ามนายหน้าหรือข้ามคู่สัญญา (ต้องสร้างข้อมูลก่อน) ส่วนเส้นทาง POST ของสัญญาฝั่งนายหน้ายังไม่ได้เทสเลย
- ลิงก์แชร์ห้องแบบสาธารณะ (`public/room-shares/:token`)
- รายการผู้เช่า สัญญา ใบแจ้งหนี้ และหนังสือยืนยันค่าคอมมิชชั่น: ข้อมูลตัวอย่างยังไม่มีรายการเหล่านี้ เทสจึงตรวจได้แค่ว่าตอบเป็นรายการ เทสข้อที่ตรวจไม่ได้จะมีป้าย "ไม่ได้ตรวจ" ในรายงาน HTML
- เพดาน 30 รายการของตัวเลือกลีดและห้องในฟอร์มสร้างผู้เช่า: ข้อมูลตัวอย่างของทีมตอนที่เขียน (12 ต.ค. 2026) มีลีด 9 ราย ห้อง 30 ห้อง จึงยังไม่เกินเพดาน ป้าย "ไม่ได้ตรวจ" ในรายงาน HTML ของแต่ละรอบบอกจำนวนลีดที่เลือกได้ และจำนวนห้องที่นับจาก `GET /agent/listings`
- การค้นบัญชีเจ้าของห้อง: การกรองเฉพาะบัญชีที่มีบทบาท landlord (ชื่อเดิม owner) ยังไม่ถูกตรวจ เพราะเทสไม่มีบัญชีที่รู้แน่ว่าไม่มีบทบาท landlord ให้ค้นเทียบ (บัญชีตัวอย่างมีทุกบทบาท)
- เส้นทางที่เพิ่มใน commit `74787c1`: จับคู่ห้องให้ลีด (`agent/leads/:id/match-*`) และนัดดูห้อง (`agent/leads/:id/viewings`, `agent/viewings`)
- บิลค่าเช่า (`bills/*`): `bills.spec.ts` ตรวจแค่ 401, 404 ของ id ที่ไม่มีจริง, 400 ของ id ผิดรูปแบบ และรายการสลิปที่รอนายหน้าตรวจ ยังไม่ได้เทสขั้นตอนอัป ส่ง ยืนยัน และตีกลับสลิป ชนิดและขนาดไฟล์ บิลของผู้ใช้อื่น และ 403 ของบทบาทที่ไม่ตรง (ต้องมีบิลในฐานข้อมูลก่อน และบัญชีตัวอย่างมีทุกบทบาท) และไม่เรียก `GET bills/mine`, `bills/mine/next`, `bills/received` ด้วยบัญชีที่ล็อกอิน (ยกเว้นเทส 401) เพราะ 3 เส้นทางนี้สร้างบิลและเปิดสถานะการเข้าพักเองก่อนตอบ
- เทสหน้าเว็บ
- กลุ่มสถานะ `viewing` ของลีด: ข้อมูลตัวอย่างไม่มีนัดดูห้อง ตัวกรองนี้จึงถูกตรวจแค่จำนวน ยังไม่ได้ตรวจรายลีด จนกว่าจะมีเทสที่สร้างนัด
